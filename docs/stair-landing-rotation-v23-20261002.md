# v23: 계단참 회전 완료와 하강 중앙값 입력

기존 FSM/ROS 노드를 유지하고 계단참의 회전 목표 판정과 하강 입력 설정을 수정했다. 정책명은 `2026-10-02-landing-rotation-v23`이다. 로봇/자동문 명령은 보내지 않았고 스택도 재시작하지 않았다.

## 계단참 수정

OBSERVED: 5F→RF의 `supported_region` 정책에서 회전 waypoint는 방향과 현재 차체의 계단참 지지 여부로 완료한다. 처음 회전 중심으로부터 10cm 이내 조건은 회전 완료에서 제거했다. 회전 중 병진 명령은 0이며 이전 접근 명령의 감속 잔여값도 회전으로 이어지지 않는다. 각속도 제한/변화율과 실제 관측의 지지영역 검사는 유지한다. 0명령은 하드웨어의 물리적 정지를 보장하지 않는다.

회전 완료 후 다음 횡단 목표의 깊이만 현재 위치에 맞춘다. 정확히는 첫 상승 방향에 평행한 좌표를 현재 위치에 맞추고, 두 번째 계단 쪽의 횡단 종료 좌표는 유지한다. 이동하는 것은 다음 접근/회전 waypoint 쌍뿐이며 최종 두 번째 상승 진입점은 바꾸지 않는다. 수정된 다음 회전 위치에 차체 회전 원이 들어가지 않으면 기존 목표를 유지하고 다음 이동 명령을 기존 지지영역 검사로 판단한다. 계단참이 비어 있다는 새 장애물 인식 기능을 추가한 것은 아니다.

횡단 이동과 최종 진입점은 위치 조건을 유지한다. 늦거나 이전 단계의 관측으로 waypoint를 넘기지 않으며, 한 관측을 재사용해 여러 waypoint를 연달아 완료하지 않는다. 별도의 고정 정지시간은 추가하지 않았다. 기존 3F→4F의 waypoint 정책, 상승 조향 v22, 계단 진입 v21, 옥상 회전 정책은 유지한다.

## BAG 비교

대상은 `ui_test_20261002_034622_ce8c9ff1.bag`에서 추출한 실제 LiDAR 자세와 진단이다. 원본 BAG을 수정하지 않았다.

OBSERVED: 기존 코드에 기록된 계단참 자세를 넣으면 742회 평가 동안 첫 회전 index=1에 머문다. 수정본은 359번째 평가, 03:47:54.029에 index=2(횡단 이동)로 전이한다. 당시 방향 약85.2°, 최초 중심과 거리 약1.09m이다. 수정본은 그때까지 첫 회전 중 병진 명령이 모두 0이었다. 기존 코드에서는 전체 742회 중 674회 병진 명령이 있었다. 비교 구간 길이가 다르므로 이 횟수를 비율 개선으로 해석하지 않는다.

INFERRED: 이번 실행에서 다음 이동을 막은 원래 위치 복귀 조건을 제거했으므로 계단참 진행 불능 원인 하나를 해소했다. UNVERIFIED: 수정된 명령으로 실제 이동 궤적/미끄럼/완주가 개선되는 정도. 기록된 동일 자세를 넣는 비교는 수정 후 물리 궤적을 재현하지 않는다. 따라서 새로운 waypoint로 전이한 뒤의 반사실적 물리 주행을 성공으로 계산하지 않았다.

## 하강 중앙값

사용자가 확인한 방향은 아래를 바라보는 전진이다. 기록 공백은 중앙값 선택의 차단 조건으로 사용하지 않는다. 보이지 않는 시각의 입력을 0이나 직전 값으로 복원하지 않고, 관측된 비중립 조작의 시간 가중 중앙값을 구간별 기준 입력으로 사용한다.

|구간|설정한 정규화 전진 입력|기존 내부 전송 단위로의 변환|
|---|---:|---:|
|상부 긴 하강|0.09|0.09 × 0.55 = 0.0495|
|하부 긴 하강|0.10|0.10 × 0.55 = 0.055|

OBSERVED: `stair_profiles.yaml`의 `stair_5f_rf_down.downhill_forward_inputs`가 두 값을 보관한다. 기존 supervisor의 두 비-LiDAR 상승/하강 구간 명령 함수에서 해당 값을 읽고, 기존 transport 정규화를 거친 최종 `request_twist.x`가 각각 0.09/0.10이 됨을 시험했다. DOWN 거리의 부호도 전진에 맞게 양수로 바꿨다. 다른 프로필에는 새 입력을 적용하지 않는다. 설정 필드를 생략한 기존 호출/fixture도 호환된다.

UNVERIFIED: SDK 조이스틱 0.09와 WebSocket 입력 0.09가 펌웨어에서 동일한 물리 응답을 만드는지는 확인하지 않았다. 요청에 따라 같은 숫자를 시험 입력으로 채택한 것이며 실제 속도를 m/s로 확정한 것이 아니다. 기존 변환 계수0.55는 두 번 적용해 명령을 키우지 않도록 곱한 뒤 기존 transport에서 나누는 용도다. 숫자를 원시 조이스틱 궤적 전체의 완전한 복원으로 표현하지 않는다.

**현재 실행 스택의 LiDAR 경로는 UP 전용이다. 이번 하강 입력 반영만으로 UI에서 RF→5F 자동 복귀가 준비되지는 않는다.** 현재 LiDAR 제어는 DOWN 경로 요청을 거절하는 기존 동작을 유지한다. 옥상 두 단 하강→상부 긴 하강→계단참 회전→하부 긴 하강의 역순 LiDAR 경로/진입 기준과 연결하는 작업이 남아 있다. 현재 두 값은 긴 하강용 명령 함수와 설정에 연결된 상태이며 옥상 두 단의 별도 기준 입력을 측정했다고 주장하지 않는다.

## 검증과 적용

OBSERVED: 선택 회귀검사 237회 통과. 테스트 간 재사용으로 중복 실행이 있으므로 고유237개/전체 저장소 검증이라는 뜻은 아니다. 실제 기록의 큰 위치 변화, 회전 중 병진0, 두 번째 회전 완료, 다음 상승 진입점 유지, 지지영역 위반, 늦거나 중복된 관측, 하강 양수 부호/정규화와 잘못된 설정 거부를 포함한다. 테스트는 로봇과 연결되지 않은 가짜 transport를 사용한다.

OBSERVED: 원본 저장소 반영 후 핵심 검사21회도 통과했고, 실제 호스트의 `run.sh --check`가 통과했다. 설정 검사 결과 `configured=true`, `robot_commands_sent=0`이다. 이는 기존 두 UP 경로에 대한 설정 준비 상태이며 DOWN 준비를 뜻하지 않는다. 제한 환경의 첫 실행에서 시간 동기화 조회 권한이 없어 실패했으나, 호스트에서 같은 검사를 수행해 통과했다. 임시 ROS 캐시는 삭제했다.

독립 cold-read(sip/shower)에서 관측 재사용과 횡단 목표 재설정 실패 시 동작의 설명 부족을 발견했다. 관측별 waypoint 전이 검사와 회귀시험을 보완했고, 위에 실패 시 원래 목표를 유지하는 동작을 명시했다. mandela 점검: 설계자가 작성한 테스트/고정 자세 재생은 독립적인 물리 성공률 검증이 아니므로 실주행 성능 주장으로 확대하지 않았다. factchk: 조이스틱/API의 물리 등가성은 추론으로 확정하지 않고 미검증으로 표시했다. ssotize 읽기 점검: 운영 입력의 원본은 기존 YAML이며 코드에0.09/0.10을 하드코딩하지 않았다. 이 문서는 결과 기록이며 별도 실행 설정이 아니다.

수정 대상은 기존 `stair_feedback.py`, `configuration.py`, `supervisor.py`, `stair_profiles.yaml`, `test_landing_region.py`, 신규 `test_downhill_inputs.py`다. 기존 worktree 변경을 보존하고 이 작업의 파일 차이만 반영한다. 수정 전 백업/비교 스크립트/결과는 프로젝트의 `landing-turn-v23-20261002`에 기록 자료로 보관한다. 임시 설정 폴더는 자동 삭제했고 BAG/실행 스택은 변경하지 않았다. 코드 반영 후 적용에는 스택 재시작이 필요하다.
