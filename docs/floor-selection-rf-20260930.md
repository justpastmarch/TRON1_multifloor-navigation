# 5F→RF 운용 준비와 진입 인식 수정 · 2026-09-30

사용자가 확인한 실제 5층 진입 배치와 치수를 기준으로 기존 노드에 반영했다. 주행 명령은 보내지 않았다. `commissioned: true`는 사용자가 승인한 현장 시험 설정이며, RF 실주행 성공을 의미하지 않는다.

## 적용 내용

- UI의 실제 층 선택은 기존 floor manager의 `/multifloor/select_floor`를 호출한다. 지도 변경 뒤 이전 층의 위치·태그·costmap 증거를 폐기하고 다시 위치를 확인한다. READY인 층에 맞춰 mission manager의 출발 층도 갱신한다. 목적지 이동 버튼과 구분했다.
- 시작 층의 지도 파일은 `floors.yaml`에서 찾는다. 5층으로 실행하면서 3층 지도를 읽던 기본값 불일치를 수정했다. 기본 시작 층 3F는 유지하고 이번 세션만 5F로 실행했다.
- 5F→RF: 첫 10단, 계단참 회전, 다음 9단, 1.35×1.48m 상부 평지 중앙, 우측 90°, 추가 2단, EXIT_CONFIRM. 추가 구간 동안 stair 모드는 유지한다. 기존 3F→4F는 원래 7개 단계다.
- RF 시험 단계 예산 합계 350초, 전체 profile 380초. 추가 구간을 기존 300초 예산에 억지로 넣지 않는다.
- 상승 입력 하한/상한 0.55, 평지 보정 속도 상한 0.06, 각속도 상한 0.2 등 기존 제어값을 재사용한다. 입력값을 실제 측정 속도로 간주하지 않는다.
- RF 첫 단과 연결되는 앞쪽 경계만 기존 0.12m 여유만큼 조정한다. 측면·후방 여유를 줄이지 않으며, 진입 높이와 위치 검사를 유지한다.
- 위치 확인 대기에서 미세 밀림 허용은 0.03m/s, 0.04rad/s. 관측된 약 0.019m/s가 기존 0.01m/s 조건에 걸렸다. 센서 신선도는 최대 0.5초 그대로이며, 두 PC 간 최대 10ms의 작은 미래 시각만 허용한다. 11ms 미래·오래된 데이터·0.10m/s 이동은 테스트에서 거부한다. 지도-스캔 일치 확인과 탐색 중 변위 검사는 유지한다.

## 핵심 수정: 1.7° 고정 거부 제거

OBSERVED. 최종 점군에서 unconstrained GICP가 제시한 중력축 성분은 약 −0.032였고, 이전 `abs(R[2,0]) > 0.03` 조건 때문에 진입을 거부했다. 약 1.9° 차이가 약 1.7° 기준을 넘은 사례다.

현재는 최종 적용할 변환의 회전을 yaw만 남겨 수직축을 보존하고, 그 변환으로 점군을 실제 변환한 뒤 같은 voxel 크기와 대응점 거리로 fitness/RMSE를 다시 계산한다. 기존 최소 fitness, 최대 RMSE, 후보 간 구별 조건과 추정 보정량 한계는 유지한다. 수직축 반전도 거부한다. 작은 solver 기울기 자체를 독립 거부 사유로 사용하지 않는다.

같은 점군의 최종 변환 fitness 0.9760, RMSE 약 0.1623m로 기존 0.18m 기준을 만족했고 진입 영역 검사도 통과했다. 이는 점군 일치도이며 독립적으로 측정한 로봇 위치 오차가 아니다. 원본과 수직축 보존 결과가 잘 맞지 않는 합성 사례는 거부하는 테스트를 추가했다. 관련 59개 테스트 통과: 새 진입 검사 3, mission handoff 7, 기존 field control 49.

## 통신·녹화 검증

OBSERVED. 최초 LiDAR 계산 자체는 약 0.07초였지만 입력 지연은 약 27초였다. 미니PC에서 카메라와 LiDAR TCP 전송 대기열이 확인됐다. 기존 카메라 중계 노드의 무선 입력을 압축 영상으로 바꿨으며 새 상시 ROS 노드는 추가하지 않았다.

재시작 후 15초간 150개 상태에서 위치 정보 나이 중앙값 0.326초, 최대 0.526초였다. 이후 사용자가 전원을 다시 켜기 전 통신 단절도 관측했으므로, 짧은 정상 구간을 영구적 통신 보장으로 해석하지 않는다.

UI 녹화는 원본 LiDAR·IMU·조이스틱·상태·명령을 유지한다. 카메라의 중복 비압축 영상은 제외하고 RGB/IR JPEG와 depth compressedDepth, 카메라 정보를 저장한다. 크기·파일 분할 제한은 추가하지 않았다.

| 정지 상태 녹화 시험 | 지연 중앙값 | 최대 |
|---|---:|---:|
| 녹화 전 | 0.257초 | 0.358초 |
| 녹화 중 | 0.357초 | 0.457초 |

약 220MB의 시험 BAG은 정상 종료·저장을 확인한 뒤 해당 BAG과 로그만 삭제했다. 기록: [recording-check.json](codex-records/floor-selection-rf-20260930/recording-check.json). 실제 이동 중 녹화 성능은 UNVERIFIED다.

## 지도 서비스 호환성과 실시간 확인

OBSERVED. `/change_map` 응답의 지도 필드는 비어 있었고 `/map`에는 정상 지도가 발행됐다. 공식 Noetic map_server의 `changeMapCallback`도 성공 결과만 설정한다. 따라서 변경 후 `/static_map`에서 실제 지도를 읽고 설정된 지도 identity와 비교한다. 출처: https://raw.githubusercontent.com/ros-planning/navigation/noetic-devel/map_server/src/main.cpp

실제 UI API의 5F 선택 요청이 accepted=true였다. 기존 5층 진입 좌표를 초기 추정으로 전달한 뒤 FloorState=5F/READY, Supervisor=NAV/connected를 확인했다. 최종 재시작 후 지도 일치 hit_fraction=0.8333, score=0.7580, LiDAR 관측 나이 약 0.250초였다. UI 경로 검토는 NAVIGATION → STAIR → FLOOR_TRANSITION, blockers=[], can_start=true였다. 이는 준비 상태이며 실행 성공 판정이 아니다. 전체 RF 주행과 실제 도착 태그 인식·도착점 유지 성공은 아직 UNVERIFIED다.

## 검증 한계와 다음 시험

오프라인 상태머신·형상 검사는 실물 폐루프 주행 성공의 대체물이 아니다. RF 상부 평지는 사용자 치수에 기반하며 독립 측량 결과가 아니다. 초기에 저장한 점군과 이후 별도 시점 점군을 사용했지만 절대 위치 정확도 ground truth는 없다. 자동문 요청은 사용하지 않고 사용자가 문을 열어둔다. 하강·사진 순회·이메일 완성 여부를 이번 상승 기능의 구현으로 간주하지 않는다.

실행 UI는 http://127.0.0.1:8765/ 이다. 실제 층 5F와 READY를 확인하고 RF 도착점을 선택한다. 테스트 버튼은 녹화를 포함하고 정지는 해당 임무 취소와 해당 녹화 종료를 요청한다. 실제 첫 주행은 계단참 및 추가 두 단 전환을 포함해 센서·명령·조이스틱 기록으로 다시 평가한다.

검토 메모: 고정 기울기 컷 대신 실제 적용 변환을 재평가하는 변경을 별도 검토했다. 후보 간 점수와 정합 잔차는 물리적 위치 정확도 증명이 아니다. 기존 가까운 후보 중 첫 후보를 유지하는 중복 제거 방식은 이번 변경에서 유지했다.
