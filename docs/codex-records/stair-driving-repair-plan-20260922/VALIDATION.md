# 계획 검증 범위

- 요청은 해결 계획 보고로 해석했다. 운영 파일 변경·새 BAG 재생·실기 명령은 수행하지 않았다.
- 현재 supervisor·stair_feedback·ros_lidar·ros_node와 경로 후보, 기존 제어 평가를 대조했다. 모드 응답 중 명령, 완료 뒤 경계 검사, phase_test 파싱·시간 제한, 설정 출처는 코드 근거다. 물리적 원인은 확정하지 않았다.
- sip/shower: 핵심 계획 발췌를 맥락 없는 별도 검토자에게 제공했다. 단계 완료 조건, 관측 이상 시 명령, 미검증 경로의 실기 허용 범위와 연결시험을 구체화했다. 마지막 수정 발췌는 stands on its own 판정. 전체 코드/실기 검증을 뜻하지 않는다.
- mandela: 동일 LiDAR로 만든 경계와 궤적의 일치를 독립 정확도처럼 취급하지 않는다. 수동 BAG가 가상 명령에 반응했다고 가정하지 않는다. 후보가 모든 과거 궤적을 통과하도록 경계를 바꾸는 순환 평가를 금지했다.
- factchk: 사실 주장은 실제 코드·검증 JSON·기록으로 확인했고, 구조/알고리즘 변경은 설계안으로 분리했다. ROS upstream 동작이나 물리 성능에 대한 외부 사실 주장을 새로 하지 않았다.
- ssotize 읽기 전용: 과거 route-evidence의 구현 제한 설명과 현재 코드의 차이를 확인해 문서에 시점 구분을 넣었다. 과거 원본 문서는 수정하지 않았다.
- re0: 검토 지적을 해당 단계에 통합하여 불필요한 별도 승인 단계 없이 실행 가능한 계획으로 정리했다.
- detool: TRON 전용 구현 계획으로 도구 독립성을 주장하지 않아 적용하지 않았다.
- HTML은 기존 검증된 문서 스타일을 재사용했다. 구조·로컬 링크·목차를 검사했으며 이번 턴에서 새 브라우저 시각 검증은 수행하지 않았다.
- 임시 로봇/ROS/브라우저 프로세스 없음. 이 폴더의 계획·생성기·검증 기록만 보존했다. 운영 Git과 주요 파일 해시 비교는 verification.json에 있다.
