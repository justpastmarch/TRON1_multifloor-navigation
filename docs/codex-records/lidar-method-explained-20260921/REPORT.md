# TRON 계단 LiDAR 측위 개선

**발견 과정과 작동 원리, ICP·FAST-LIO와의 관계**

작성일: 2026-09-21 · 기준 구현: `gyro-gicp-installed-20260921-v1` · 설명 대상: RViz에서 녹색으로 확인한 개선 측위

> **이번 개선은 새로운 ICP를 발명하거나 FAST-LIO의 내부를 고친 작업이 아니다. 원래 사용하던 GICP 앞에 올바른 중력 초기화와 IMU 회전 예측을 붙이고, 뒤에는 실패한 측정을 새 위치처럼 보여 주지 않는 처리를 넣은 것이다.** 그 결과 두 계단 BAG에서 놓치던 계단참 회전을 추적하고, 주변 점군을 더 일관되게 연결할 수 있었다.

이 문서는 실제 코드와 남아 있는 실험 기록으로 발견 과정을 재구성한다. 기록에 없는 판단이나 실패 원인을 나중에 확정 사실처럼 채워 넣지 않는다. **OBSERVED**는 코드·기록·재계산에서 확인한 것, **INFERRED**는 그 근거로 해석한 것, **UNVERIFIED**는 외부 실측이나 실기 시험이 필요한 것이다. 일반 이론은 원 논문·공식 구현과 구분해 설명한다.

## 2. 먼저 계층을 구분해야 한다

같은 대화에서 ‘LiDAR’, ‘ICP’, ‘FAST-LIO’, ‘RViz’, ‘Supervisor’를 함께 부르면 서로 대체 가능한 제품처럼 들릴 수 있다. 실제로는 역할이 다르다.

| 계층 | 무엇을 하는가 | 이번 시스템의 예 |
|---|---|---|
| ① 센서·원시 데이터 | 거리를 측정하고 각속도·가속도를 기록한다 | Livox LiDAR 점군, IMU, wheel odometry |
| ② 시간·좌표·전처리 | 같은 시각·축으로 해석하고 점 수를 줄인다 | header 시각, IMU↔LiDAR 회전, 거리 필터, voxel |
| ③ 운동 예측·정합 | 다음 자세를 예측하고 현재 점군을 지도에 맞춘다 | gyro 적분, GICP |
| ④ 연속 측위 | 여러 scan의 자세·지도·유효 상태를 관리한다 | 이번 gyro 보조 GICP 추적기 / 다른 설계인 FAST-LIO2 |
| ⑤ 경로·상태 판단·제어 | 현재 위치를 목표와 비교해 움직임을 결정한다 | Stair Supervisor, 계단참 전환, 중심선 보정 |
| ⑥ 표현·운영 | 결과와 상태를 보여 주고 임무를 요청한다 | RViz, 웹 UI, mission manager |

**GICP는 ③의 부품이다. 이번 개선 전체는 ②~④를 묶은 추적기이고, FAST-LIO2는 자체 방식으로 ②~④를 구현한 더 넓은 측위 시스템이다.** Stair Supervisor는 그 결과를 소비하는 다음 계층이다. 실제 package 경계가 이 표와 일대일로 같다는 뜻은 아니며, 이해를 위한 기능 구분이다.

```text
원본 LiDAR ── 전처리 ─────────────────────┐
                                        ▼
IMU ── 축 변환 ── 초기 중력 / 짧은 회전 예측 ── GICP 정합
                                        │
최근 수락 scan 지도 ─────────────────────┘
                                        ▼
                           수락 여부 + 측정 시각 + 위치·자세
                              ├─ RViz: 그림으로 표시
                              └─ Supervisor: 경로와 비교 → 속도 명령
```

이 구조는 원본 센서에서 시작한다. **발산한 FAST-LIO 위치를 다시 정렬해 녹색 위치를 만든 구조가 아니며, wheel odometry를 녹색 위치의 정답으로 주입한 구조도 아니다.** [로컬 코드 C1, C2]

## 3. 어떻게 해결 방법을 찾았는가

### 3.1 출발점은 ‘그림이 이상하다’는 관찰이었다

이 문서의 `102101`, `103313`, `105713`은 2026-08-27에 기록된 BAG 파일 이름의 시각 부분이다. 예를 들어 `105713`은 `stair_3F_to_4F_UP_20260827_105713.bag`를 뜻한다. 서로 다른 세 기록이지 알고리즘 버전 번호가 아니다.

사용자는 같은 BAG을 RViz에서 비교했을 때 FAST-LIO·LiDAR·odom이 크게 벌어지고, 계단참을 돌아 반대 방향으로 올라가야 하는데 LiDAR가 그 회전을 따라가지 못하는 것 같다고 지적했다. 이 관찰은 실제 문제의 단서였지만, 화면만으로는 원인을 한 가지로 정할 수 없었다.

가능한 구분은 적어도 세 가지였다. 첫째, **좌표계가 기울어져 그림이 잘못 보이는 문제**. 둘째, **시간에 따른 회전 추적 자체가 중단된 문제**. 셋째, **서로 다른 원점·시각의 궤적을 겹쳐 비교한 문제**다. FAST-LIO의 필터 발산은 이들과 또 별도로 조사해야 했다.

### 3.2 첫 번째 구체적 결함: ‘가장 큰 평면 = 바닥’

**OBSERVED:** 기존 `level_transform_from_plane()`은 초기 점군 전체에서 RANSAC으로 우세 평면 하나를 찾고, 그 법선이 세계 좌표의 +Z가 되도록 회전시켰다. 바닥인지 확인하는 별도 의미 판정은 없었다. 세 기록에서 초기 센서 Z축의 기울기는 약 89°였고, 한 기록의 계산값은 약 89.62°였다. [기록 H1, 코드 C3]

**INFERRED:** 계단 입구에서는 벽이 바닥보다 넓고 많은 점을 차지할 수 있다. 당시 추출 법선이 IMU 가속도의 위쪽 방향과 거의 직각이었던 점을 함께 보면, 우세 평면으로 벽을 선택한 것으로 해석된다. 모든 원본 점에 사람이 바닥/벽 라벨을 붙여 증명한 것은 아니다.

따라서 바닥 방향을 임의의 우세 평면으로 정하는 대신, **초기 저동역학 구간의 가속도 방향을 사용해 중력에 맞춘 좌표계를 만드는 것**을 후보로 삼았다. 이는 높이와 roll/pitch를 해석할 기준을 바로잡는 변경이다.

여기서 중요한 점이 있다. 좌표계 전체를 일정하게 돌리는 것만으로는 잘못된 상대 회전 추적이 자동으로 해결되지 않는다. 수평 초기화 문제와 계단참 추적 유실 문제를 같은 문제라고 단정하지 않았다.

### 3.3 두 번째 결함: 정합이 실패하면 예측이 뒤처진 채 고정됐다

**OBSERVED:** 기존 처리 루프는 마지막으로 수락한 자세를 다음 GICP의 초기값으로 사용했다. 정합이 거절되면 자세와 지도는 갱신하지 않았다. 다음 scan에서도 그 오래된 자세를 다시 초기값으로 사용했다. [코드 C3]

정상적으로 매 scan이 들어맞는 동안에는 직전 자세가 괜찮은 초기값일 수 있다. 그러나 회전 중 몇 번 거절되면 초기값은 ‘직전 실제 자세’가 아니라 **몇 초 전 마지막으로 성공했던 자세**가 된다. 실제 로봇은 계속 돌아가므로 새 점군과 오래된 지도/초기 자세의 차이가 커진다.

이렇게 한 번 뒤처지면 다음 정합도 실패하기 쉬운 구조였다. 특히 수락 검사까지 오래된 자세를 기준으로 하므로, 실제 회전을 따라잡은 후보가 오히려 큰 변화라고 거절될 가능성도 있다. 그 구조는 코드에서 확인했고, 모든 최초 거절이 어느 단일 요인 때문에 발생했는지까지 분리 증명한 것은 아니다.

**OBSERVED:** `105713`에는 166프레임 연속 거절, 첫 거절과 마지막 거절 사이 약 33초가 기록됐다. 여기서 연속 거절 구간은 첫 거절과 마지막 거절 프레임의 시각 차이로 정의했다. 약 0.2초 간격의 추적에서 몇 초를 잃는 문제가 아니라, 회전 구간 전체를 잃을 수 있는 길이였다. [H1]

### 3.4 세 번째 결함: 실패한 자세를 새 시각으로 다시 출력했다

**OBSERVED:** 기존 코드는 정합이 거절돼도 마지막 자세로 새 점군을 변환하고, 새 sensor timestamp의 odometry·path·cloud를 계속 작성했다. 지도 갱신 여부는 검사했지만, 현재 측정 출력 자체는 성공에 묶여 있지 않았다. [C3]

이 경우 화면에는 메시지가 계속 들어오므로 추적기가 살아 있는 것처럼 보인다. 하지만 실제 내용은 **새 위치 측정이 아니라 오래된 위치의 반복**이다. 이것은 위치 오차와 별개로 관측의 유효성을 잘못 표현하는 문제다.

해결은 그림을 더 부드럽게 만드는 것이 아니라, 실패를 실패로 표시하는 것이었다. 이 처리는 좋은 프레임의 위치를 더 정확하게 만드는 알고리즘은 아니지만, 이후 제어가 오래된 위치를 현재 위치로 오인하지 않도록 하는 데 필요하다.

### 3.5 그래서 ‘초기화만 수정’과 ‘회전 예측도 추가’를 나눠 보았다

당시 `105713`에 대한 축 일치 가정 실험 기록은 다음과 같다. 아래는 **최종 설치 결과가 아니라 원인 분리를 위한 중간 실험**이다. 마지막 상대 yaw는 각 처리 결과의 첫 센서 자세에 대한 마지막 상대 회전에서 계산한 yaw이며, 절대 건물 방위가 아니다.

| 실험 | 수락 프레임, 초기화 포함 | 최장 연속 거절 구간 | 마지막 상대 yaw |
|---|---:|---:|---:|
| 기존 방식 | 168/340 | 약 33.0초 | 약 -2.6° |
| 중력 초기화만 변경, IMU·LiDAR 축 일치 가정 | 165/340 | 약 33.6초 | 약 -0.8° |
| 중력 초기화 + gyro 회전 예측 + GICP, 축 일치 가정 | 340/340 | 없음 | 약 +178.3° |

중력 초기화만으로 추적 유실은 해결되지 않았다. 회전 예측을 넣은 후보에서는 같은 분석 구간에서 유실이 사라졌다. **따라서 관측한 개선을 단순히 RViz의 지도를 똑바로 돌린 효과라고 설명할 수 없다.** 동시에 여러 처리 조건이 관련되므로 gyro만의 보편적 개선율을 산출한 실험이라고도 말하지 않는다. [H1의 분리 실험, `metrics.json`]

당시 gyro만 적분한 마지막 각도는 약 +151.4°였다. 정합을 합친 +178.3°와 다르다. 이 비교는 해당 중간 실험에서 두 출력이 동일하지 않다는 근거다. 어느 각도가 실제 회전에 더 가까운지를 외부 기준으로 검증한 결과는 아니다. 코드에서도 최종 pose를 gyro가 아니라 GICP 결과로 갱신하는 것을 확인했다.

### 3.6 센서 축의 실제 설정을 반영하고 원본 BAG으로 재검증했다

사용자는 기록 당시와 현재 설정이 같다고 확인했다. 이를 근거로 현재 FAST-LIO YAML에 기록된 **LiDAR→IMU 초기 회전 행렬**을 가져오고, 그 역회전으로 IMU 벡터를 LiDAR 축에 맞췄다.

축 일치 가정은 최종 구현에 남기지 않았다. 실제 처리 코드가 원본 BAG의 IMU·LiDAR를 읽도록 적용한 뒤, 기존과 동일한 header 시각의 프레임을 재계산했다. 초기 캐시 기반 후보와 최종 설치 버전의 숫자는 조금 다르므로 이 문서는 최종 수치 표를 따로 둔다. [H2, H3]

사용자가 RViz에서 시각적으로 확인한 두 기록은 `102101`, `105713`이다. `103313`은 수치 회귀 확인용이며, 세 기록 모두가 동일한 180° 정상 주행이었다고 가정하지 않았다.

## 4. 좌표계: 비슷해 보이는 두 보정을 혼동하면 안 된다

### 4.1 IMU↔LiDAR 회전과 LiDAR↔몸체 장착은 다른 값이다

| 변환 | 목적 | 이번 사용 |
|---|---|---|
| IMU → LiDAR | gyro·가속도 벡터를 점군과 같은 축에서 해석 | YAML의 `mapping/extrinsic_R` 역회전 |
| LiDAR → body/base | 센서 원점의 측위를 로봇 중심 위치로 바꿈 | 별도 몸체 장착값: XY 중앙, 높이 0.18m, pitch +5° |
| local → stair profile | 이번 측위의 임의 시작점을 실제 계단 경로에 연결 | 진입 anchor; 추적과 별도 문제 |
| local → building map | 건물 도면·층 지도상의 절대 위치로 연결 | 이번 추적 개선만으로 해결하지 않음 |

사용자가 확인한 **18cm와 +5°를 IMU–LiDAR 보정 행렬 대신 넣으면 안 된다.** 전자는 몸체와 센서의 관계이고, 후자는 센서 내부/장착 기준에서 IMU와 LiDAR의 축 관계다.

### 4.2 행렬 기호를 하나로 통일하면

이 문서에서 `T_A_B`는 **B 좌표의 점을 A 좌표로 바꾸는 변환**이다. `R_A_B`는 그 회전 부분이다.

```text
p_A = R_A_B · p_B + t_A_B
```

설정의 `extrinsic_R`는 로컬 코드에서 LiDAR→IMU로 해석한다. gyro를 LiDAR 축에서 쓰려면 반대 방향이므로 다음과 같다.

```text
R_L_I = transpose(R_I_L)
ω_L   = R_L_I · ω_I
a_L   = R_L_I · a_I
```

회전 행렬의 역행렬은 전치행렬이다. 현재 로더는 유한값·직교성·양의 determinant를 확인하고 `Rotation.from_matrix()`로 회전 표현을 만든 뒤 전치한다. 단순히 YAML 숫자를 아무 축에나 적용한 것이 아니다. [C1: `load_imu_rotation`]

위치 결과를 몸체로 옮길 때는 다음을 사용한다.

```text
T_local_body = T_local_lidar · inverse(T_body_lidar)
```

XY 장착 오프셋이 0이더라도 높이 오프셋과 회전은 남는다. 기체가 pitch/roll로 기울면 높이 방향의 센서 레버암이 수평 위치 차이에도 영향을 줄 수 있다. 그러므로 “위에서 볼 때 같은 XY”와 “항상 센서 pose가 몸체 pose와 같다”는 같은 말이 아니다.

### 4.3 중력으로는 yaw를 알 수 없다

초기 가속도 방향을 +Z에 맞추면 roll/pitch 기준을 정할 수 있지만, 그 축 둘레로 어느 쪽이 건물 북쪽인지까지 정하지는 못한다. 이번 방법은 자력계나 측량 기준을 추가하지 않았다.

따라서 첫 자세를 기준으로 ‘180° 돌아왔다’고 추적할 수 있는 것과, 건물 지도에서 ‘북쪽을 향한다’고 아는 것은 다르다. **계단 경로 원점과 방향을 맞추는 진입 정합이 여전히 필요한 이유**다.

## 5. 현재 방식이 한 프레임을 처리하는 순서

### 5.1 입력과 전처리

원본 LiDAR 메시지에서 `(x, y, z)`를 읽고, 유한값이며 센서로부터 0.5~20m 안에 있는 점을 사용한다. 기준 설정은 매 두 번째 LiDAR packet을 처리하고, 20cm voxel로 점을 줄인다. 기록된 세 구간의 처리 간격 중앙값은 약 0.2초다.

voxel은 작은 3차원 격자 안의 여러 점을 대표점으로 줄이는 연산이다. **voxel 20cm는 위치 정확도가 반드시 20cm 단위라는 뜻이 아니다.** 정합 변환 자체는 연속값으로 계산한다. 반대로 20cm voxel을 쓴다고 계단의 모든 작은 형상이 보존된다는 뜻도 아니다.

GICP에 넘기기 전 점군에는 반경 `3 × voxel = 0.6m`, 최대 이웃 30개를 사용해 법선을 계산한다. source와 local map을 정합 함수에 넣을 때도 voxel 처리한다. 법선은 주변 표면이 어느 방향을 보는지 나타내며, 뒤의 GICP가 사용하는 국소 표면 구조에 해당한다. [C1, C2]

### 5.2 최초 한 번: 가속도 중앙값으로 위쪽 방향을 정한다

초기 LiDAR 시각 `t₀`를 중심으로 앞뒤 0.5초의 보정된 가속도 표본을 고르고, 축별 중앙값을 구한다. 그 벡터를 정규화해 위쪽 방향으로 사용한다.

```text
u = normalize(median(a_L(t)), t ∈ [t₀−0.5, t₀+0.5])
R₀ · u = [0, 0, 1]ᵀ
```

중앙값은 초기 표본의 순간적인 흔들림에 덜 민감하게 하려는 선택이다. 다만 **가속도계는 중력만 측정하는 센서가 아니므로**, 로봇이 강하게 움직이는 구간의 중앙값이 참된 수직을 보장하지 않는다. 이 코드에는 초기 물리적 정지 상태를 별도 인증하는 완성된 검출기가 없다.

초기화는 첫 좌표계를 만드는 일이다. 첫 scan에는 아직 다른 scan과 맞춘 결과가 없으므로 `BOOTSTRAP`이며 `geometry_valid=false`다. 첫 자세를 만들었다는 사실과 기하 측정이 성공했다는 사실을 분리한다.

**오프라인/실시간 차이:** BAG 파일에서는 미래 0.5초를 읽을 수 있다. 실제 스트리밍 구현은 그 시각의 표본이 실제로 도착할 때까지 기다린다. 미래 센서를 미리 아는 알고리즘으로 운용하는 것이 아니다. 시작 전에 충분한 과거 구간도 필요하다. [C1의 초기화 구간 검사]

### 5.3 다음 scan: 자이로로 회전만 예측한다

IMU 표본의 시각은 BAG에 기록된 시각이 아니라 메시지의 측정 header 시각이다. 인접 표본 사이의 평균 각속도로 작은 회전을 계산한다.

```text
ω̄ᵢ = (ωᵢ + ωᵢ₊₁) / 2
ΔRᵢ = Exp(ω̄ᵢ · Δtᵢ)
R(tᵢ₊₁) = R(tᵢ) · ΔRᵢ
```

여기서 `Exp`는 3차원 회전 벡터를 회전 행렬로 바꾸는 연산이다. yaw 숫자에 z축 각속도만 더하는 방식이 아니다. pitch·roll이 있는 계단에서 센서의 세 회전축을 함께 취급한다. 필요한 LiDAR 시각 사이의 자세는 Slerp로 보간한다. [C2: `ImuRotation`]

마지막으로 **수락한** LiDAR 시각을 `tₖ`, 현재 시각을 `t`라 하면 다음 초기값을 만든다.

```text
R_pred(t) = R_accepted(tₖ) · ΔR_gyro(tₖ → t)
p_pred(t) = p_accepted(tₖ)
```

`R_accepted`는 마지막 수락 시각의 LiDAR 축을 local 좌표로 옮기는 회전이다. `ΔR_gyro(tₖ → t)`는 현재 LiDAR 축을 그 마지막 시각의 LiDAR 축으로 연결하는 상대 회전이며, 이미 IMU→LiDAR 축 변환을 적용해 계산한다. 따라서 오른쪽에 곱해 `현재 LiDAR → 이전 LiDAR → local` 순서로 연결한다.

두 번째 줄이 중요하다. **이번 추적기는 IMU 가속도에서 이동 위치를 적분하지 않고, 일정 속도 모델로 평행 이동을 예측하지도 않는다.** 초기 평행 이동은 마지막 수락 위치를 유지하고, 새 위치는 GICP가 점군으로 찾아낸다.

코드 내부에서는 IMU 창 전체의 누적 회전 표현을 만들 수 있지만, 실제 초기값에 사용하는 것은 두 시각 사이의 상대 회전이다. 매번 IMU 누적 자세를 세계 좌표의 절대 정답으로 사용하는 것이 아니다. 유실이 길어지면 상대 적분 구간도 길어져 그 장점이 약해진다.

### 5.4 최근 지도에 GICP로 맞춘다

source는 현재 scan이고, target은 최근에 수락한 최대 15개 scan을 local 좌표로 옮겨 쌓은 지도다. 약 5Hz로 연속 수락하는 상황이라면 약 3초 분량에 해당하지만, 실제 보관 기준은 시간 3초가 아니라 **수락 scan 15개**다.

현재 scan을 gyro 예측 자세에서 출발시켜 지도에 맞춘다. 결과는 회전과 평행 이동을 함께 포함하는 6자유도 변환이다. 이후 자세는 gyro 예측값 그대로가 아니라 이 기하 정합 결과로 갱신한다.

최근 지도는 관측들이 이미 추정된 pose로 배치된 결과다. 측량된 절대 지도는 아니다. 이전 pose가 잘못되면 지도도 잘못 쌓일 수 있고, 그 지도와 잘 맞는다는 사실만으로 절대 위치 정확도를 입증할 수 없다.

### 5.5 수락 검사는 ‘이전 위치에서 얼마나 변했는가’가 아니라 ‘예측에서 얼마나 고쳤는가’다

기준 구현은 다음 보정 변환을 계산한다.

```text
ΔT = inverse(T_pred) · T_GICP
translation_innovation = norm(ΔT의 이동 벡터)
rotation_innovation    = angle(ΔT의 회전 행렬)
```

수락에 사용한 숫자는 기존과 같다.

- fitness ≥ 0.35
- translation innovation ≤ 0.50m
- rotation innovation ≤ 0.35rad, 약 20.1°

그러나 **같은 숫자를 유지했다고 판정 의미까지 같은 것은 아니다.** 예전에는 마지막 수락 자세와 비교했지만, 지금은 현재 시각으로 회전을 예측한 자세와 비교한다. 0.35rad는 로봇이 계단에서 돌 수 있는 총 회전각의 한도가 아니다.

설명용 예를 보자. 아래 숫자는 BAG 측정값이 아니다.

| 항목 | 예시 값 |
|---|---:|
| 마지막 수락 방향 | 100° |
| 현재 GICP가 찾은 방향 | 138° |
| gyro로 예측한 현재 방향 | 136° |
| 예전 기준의 회전 차이 | 38° → 약 20.1° 한계를 초과 |
| 지금 기준의 회전 보정량 | 2° → 한계 안 |

계단참의 180° 회전도 한 scan에서 갑자기 180°를 맞추는 것이 아니라, 여러 관측 사이의 작은 회전들이 계속 연결된 결과다. 중간 갱신을 오래 잃지 않는 것이 중요하다.

정상 회전을 허용하려고 각도 한계를 180°로 늘린 것이 아니다. **정상 회전으로 예상되는 부분과 정합이 추가로 수정해야 하는 부분을 분리한 것**이다. 다만 잘못된 gyro 예측 근처의 잘못된 정합도 수락될 수 있으므로, 이 검사만으로 진실성이 인증되지는 않는다. [C2: `correction`과 `accepted` 계산]

현재 기본 수락식에는 별도 RMSE 상한이나 엄격한 최적화 수렴 인증 항목이 없다. RMSE는 기록되는 진단값이다. `max_iteration=30`에 도달했다고 반드시 정답에 수렴했다는 뜻도 아니다.

### 5.6 성공하면 지도와 마지막 관측 시각을 함께 갱신한다

수락된 점군만 local map에 추가하고, 마지막 수락 자세·시각을 바꾼다. 다음 scan의 gyro 상대 회전도 새로 수락한 시각부터 계산한다. 이 때문에 LiDAR가 계속 제대로 관측되는 동안 gyro의 장시간 누적 자세를 그대로 끌고 가지 않는다.

기존 비교 도구는 RViz용 전체 누적 지도도 따로 만들었다. 추적에 사용하는 **최근 15개 local map**과 보기 위해 저장하는 **전체 누적 cloud**는 다른 산출물이다. 전체 cloud를 저장했다고 loop closure나 전역 최적화가 구현된 것은 아니다.

### 5.7 실패하면 ‘새로운 측정 위치’를 만들지 않는다

설치된 오프라인 비교 도구는 거절된 프레임의 측정 pose를 NaN으로 기록하고, 현재 측정 odometry를 생성하지 않는다. live 경로·점군에는 빈 출력을 넣고, 복구 뒤 새 경로 구간을 시작한다. 오래된 지도가 남더라도 마지막 유효 관측 시각을 유지한다.

`PREDICTED`라는 진단 상태가 보여도 그것은 ‘실제로 LiDAR가 현재 위치를 측정했다’는 뜻이 아니다. 초기 `measurement_valid`와 `geometry_valid`도 구분한다. [H2, C4]

나중에 Supervisor용으로 옮긴 추적 코드는 `BOOTSTRAP / TRACKED / DEGRADED`와 `geometry_valid`, `last_geometry_at` 등을 사용한다. 내부에 마지막 transform이 보관돼 있어도 ROS adapter는 **새롭고 유효한 geometry 표본만** `/stair_supervisor/lidar_odom`으로 내보낸다. 오프라인 도구의 상태 이름을 현재 ROS 코드의 enum과 동일하다고 설명하면 안 된다. [C1, C5]

### 5.8 IMU 일부가 빠지면 어떻게 되는가

IMU 예측을 지원하는 시각 범위와 표본 공백을 검사한다. 기준 공백 한계는 0.03초다. 이 한계는 gyro 예측 자료의 지원 여부를 판단하는 값이지, 그 자체로 전체 로봇의 비상정지 조건이 아니다.

최종 설치 버전은 gyro 예측을 만들 수 없을 때 마지막 관측 자세를 초기값으로 같은 GICP를 시도할 수 있다. 기하 정합이 수락되면 새 시각에서 다시 이어 간다. 이후 IMU 구간이 지원되면 gyro 예측을 재개한다. 초기 연구 후보의 ‘IMU 공백 후 계속 회복하지 못할 수 있는’ 동작을 보완한 부분이다.

이 복구는 **가까운 지역에서 같은 정합기가 다시 맞을 기회를 주는 것**이다. 큰 이동을 놓친 뒤 건물 어디서든 다시 위치를 찾는 전역 재측위는 아니다.

## 6. ICP와 GICP는 정확히 어떻게 다른가

### 6.1 ICP: 대응점과 변환을 번갈아 갱신하는 틀

ICP는 대략 현재 변환으로 source를 옮긴 뒤 가까운 target 점을 짝짓고, 짝의 오차를 줄이는 변환을 반복해서 찾는다. 기본 point-to-point 오차는 다음과 같다.

```text
E(T) = Σ ||T·pᵢ − qᵢ||²
```

이는 초기값 없이 아무 방향의 두 점군을 반드시 찾아 맞추는 전역 검색이 아니다. Open3D 공식 예제도 대략적인 정렬 초기값을 입력으로 사용한다. [Open3D ICP 설명](https://www.open3d.org/docs/release/tutorial/pipelines/icp_registration.html)

### 6.2 Point-to-plane ICP: 표면에 수직인 오차를 사용한다

target의 법선 `nᵢ`를 사용하면 다음처럼 표면 수직 방향의 오차를 줄인다.

```text
E(T) = Σ [nᵢᵀ(T·pᵢ − qᵢ)]²
```

계단 옆 벽처럼 같은 평면을 서로 다른 위치에서 샘플링한 경우, 점 자체를 정확히 일대일로 겹치는 것과 표면을 맞추는 것은 다르다. 그 차이를 반영하는 방식이다. [Open3D ICP 설명](https://www.open3d.org/docs/release/tutorial/pipelines/icp_registration.html)

### 6.3 GICP: 양쪽 점군의 국소 표면 구조를 함께 반영한다

GICP는 ICP 계열 안에서 source·target의 국소 구조를 공분산 형태로 사용한다. 대표 목적함수는 잔차 `rᵢ = T·pᵢ − qᵢ`에 대해 다음과 같이 표현할 수 있다.

```text
E(T) = Σ rᵢᵀ [C_target,i + R·C_source,i·Rᵀ]⁻¹ rᵢ
```

국소적으로 평면인 표면의 방향에 따라 잔차를 다르게 평가한다. 원 논문은 이를 point-to-plane을 양쪽 표면으로 확장한 관점으로 설명한다. 여기서 공분산은 표면 오차 모델이지, 로봇 전체 위치의 확률적 신뢰도와 같은 값이 아니다. [Segal·Hähnel·Thrun, Generalized-ICP 원 논문](https://www.robots.ox.ac.uk/~avsegal/resources/papers/Generalized_ICP.pdf)

이번 구현은 Open3D 0.18.0의 `registration_generalized_icp()`를 그대로 호출한다. 우리 코드가 계산한 법선으로 Open3D가 방향성 공분산을 구성하고 GICP 변환을 계산한다. 따라서 **새로운 목적함수나 정합 솔버를 만든 작업이 아니다.** [Open3D 0.18.0 GICP 구현](https://raw.githubusercontent.com/isl-org/Open3D/v0.18.0/cpp/open3d/pipelines/registration/GeneralizedICP.cpp)

### 6.4 이번 수정 위치는 정합 엔진 ‘주변’이다

```text
수정 전: 우세 평면 초기화 → 마지막 성공 pose로 시작 → GICP → 거절해도 최신 출력
수정 후: 중력 초기화 → gyro로 현재 회전 예측 → 같은 GICP → 유효 관측만 출력
```

gyro 예측은 GICP에 들어가는 **초기값**이다. 현재 코드의 GICP 목적함수에 ‘IMU와 얼마나 차이 나는지’라는 확률적 항을 더한 것은 아니다. 결과를 예측 대비 보정 한계로 검사하지만, 이것도 Kalman 공분산 기반 융합과 같지는 않다.

그래서 가장 정확한 명칭은 **‘중력 초기화와 gyro 회전 예측을 사용하는 scan-to-local-map GICP 측위’**, 짧게는 **‘IMU 회전 보조 GICP 추적’**이다. ‘FAST-LIO를 단순화한 동일 알고리즘’, ‘완전한 tightly coupled LIO’, ‘오차 없는 ICP’라고 부르지 않는다.

## 7. FAST-LIO와는 같은 계층인가, 다른 알고리즘인가

### 7.1 비교 대상을 맞추면 둘 다 맞는 말이다

**GICP 대 FAST-LIO:** 부품 대 시스템이므로 계층이 다르다. GICP는 두 점군의 변환을 찾는 정합 방법이다. FAST-LIO는 IMU 예측과 LiDAR 관측으로 상태를 추정하고 지도를 관리하는 시스템이다.

**이번 gyro-GICP 추적기 전체 대 FAST-LIO2:** 둘 다 연속적인 pose를 만들어 주는 측위 시스템이므로 비교 가능한 계층이다. 다만 사용하는 상태·최적화·센서 결합 방식과 기능 범위가 다르다.

FAST-LIO 논문은 LiDAR와 IMU를 tightly coupled iterated Kalman filter로 결합한다. FAST-LIO2는 이 계열에서 raw point 기반 직접 정합과 incremental ikd-Tree 지도 관리를 강조한다. 이름에 ‘direct’가 있다고 데이터 전처리 없이 아무 점이나 사용하는 뜻은 아니다. [FAST-LIO 원 논문](https://arxiv.org/abs/2010.08196), [FAST-LIO2 원 논문](https://arxiv.org/abs/2107.06829), [공식 저장소](https://github.com/hku-mars/FAST_LIO)

### 7.2 설치 소스에서 확인한 구체적인 차이

아래 표의 ‘이번 방식’은 실제 기준 추적 코드, FAST-LIO 열은 로컬에 설치된 FAST-LIO 계열 소스에서 확인한 내용이다. 해당 로컬 버전에는 중력 초기화 등의 프로젝트 수정이 포함돼 있어 upstream 모든 버전과 동일하다고 가정하지 않는다. [C1, C2, C6]

| 항목 | 이번 gyro-GICP 추적 | 설치된 FAST-LIO 계열 |
|---|---|---|
| 주 상태 | 현재 pose, 마지막 관측 시각, 최근 scan, 유효성 | 위치·회전·속도·gyro bias·accel bias·중력·센서 외부 보정 상태 |
| IMU 각속도 | LiDAR 시각 사이 상대 회전 예측 | 필터 상태 예측, bias를 고려한 회전 처리 |
| IMU 가속도 | 초기 위쪽 방향 선정 | 초기화, 중력·bias와 함께 운동 예측 |
| 위치 예측 | 마지막 위치 유지; 정합이 이동을 찾음 | 속도·가속도·중력에 기반한 상태 전파 |
| LiDAR 관측 사용 | Open3D GICP에서 별도 pose 최적화 | 점-표면 잔차/Jacobian을 이용한 필터 관측 갱신 |
| IMU와 LiDAR 결합 | 초기값 보조 및 예측 대비 결과 검사 | 반복 Kalman 갱신으로 상태와 불확실도 결합 |
| 공분산 | 로봇 상태 공분산을 전파·갱신하지 않음 | 필터 상태 공분산과 process noise 사용 |
| 점별 deskew | 구현하지 않음 | IMU 구간 자세·속도·위치로 scan 내부 점을 보정 |
| 지도 | 최근 수락 scan 최대 15개 | ikd-Tree 기반 지도 관리 |
| 외부 보정 | YAML의 고정 회전만 gyro 축 변환에 사용 | 초기 외부 보정 상태 및 설정에 따른 온라인 추정 |
| gyro bias 추정 | 없음 | 초기 gyro 평균 및 상태의 bias 처리 |
| 전역 loop closure | 없음 | 이번에 확인한 FAST-LIO 코어만으로 전역 loop closure까지 수행한다고 보지 않음 |

FAST-LIO2도 관측과 지도 사이의 기하 관계를 반복 계산한다. 따라서 넓은 의미에서 scan matching을 사용한다. 하지만 **FAST-LIO2를 ‘Open3D GICP를 호출하는 프로그램’으로 설명하는 것은 틀리다.** 설치 코드는 관측 잔차와 Jacobian을 필터에 넣는 경로이며, 이번 코드는 `registration_generalized_icp()`의 결과를 pose로 받아들이는 경로다.

반대로 이번 방식은 IMU와 LiDAR가 모두 들어간다고 해서 Kalman filter가 숨어 있는 것도 아니다. 추적 핵심에서 위치·속도·bias를 묶은 공분산 상태를 찾을 수 없다.

### 7.3 왜 FAST-LIO가 발산해도 이번 방식은 나아질 수 있었나

**OBSERVED:** 당시 `102101`의 저장 FAST-LIO CSV 전체 구간에는 첫 위치 대비 약 12,726.6m의 최대 변위가 기록돼 있었다. 실내 계단 주행의 실제 이동량으로 해석할 수 없는 결과다. 설치 소스에는 유효 정합점이 없으면 관측 갱신을 무효화하는 처리도 있다. 하지만 **그 두 사실만으로 최초 발산 원인을 특정할 수는 없다.** [H1, C6]

**구조상 차이:** 이번 방법은 가속도 기반 위치 전파, 속도 상태, IMU bias·중력·외부 보정의 결합 추정 등 FAST-LIO의 여러 경로를 사용하지 않는다. 따라서 그 경로에 민감한 문제가 있었다면, 더 좁은 구조가 같은 방식으로 망가지지 않을 수 있다.

이 설명은 가능한 구조적 이유이지, 실제 발산 원인의 확정 진단이 아니다. 시간 동기, 단위, 센서 외부 보정, 초기 상태, 움직임 왜곡, 관측 퇴화 중 무엇이 최초 원인이었는지는 당시 입력과 필터 내부 상태를 함께 재현해야 판단할 수 있다. 이번 개선 결과만으로 FAST-LIO가 계단에 부적합하거나 IMU 자체가 고장 났다고 결론 내리지 않는다.

한 가지 설정상 주의점도 있다. 로컬 YAML에는 `extrinsic_est_en: false`가 있지만 센서 launch는 이를 `true`로 덮어쓴다. launch는 중력 정렬 초기화를 켜고 세계 중력 lock은 끈다. **YAML의 초기 회전을 고정 사용한 이번 추적과, 온라인에서 외부 보정 등을 추정하는 FAST-LIO의 내부 상태는 동일하지 않다.** 기록 당시/현재 설정이 같다는 사용자 확인은 실행 중 추정 상태의 동일성이나 물리적 보정 정확도의 증명이 아니다. launch 주석에 적힌 과거 실험 주장도 이번 문서에서 독립 재검증한 결과로 승격하지 않았다. [C7]

### 7.4 ‘더 단순하니 더 좋다’는 결론도 아니다

이번 방식의 장점은 문제 범위가 좁고, 각 단계의 실패를 관찰하기 쉽다는 것이다. 반면 가속·회전이 큰 상황의 deskew, 체계적인 bias 추정, 상태 불확실도 관리가 빠져 있다. 관측이 잘 맞는 이번 구간에서 좋아졌다는 사실과, 어떤 환경에서도 FAST-LIO보다 좋다는 주장은 다르다.

올바른 비교는 같은 원본 데이터·같은 몸체 기준·같은 시간에 두 측위 결과를 만들고, 외부 기준 위치에 대한 오차와 실패·복구·지연을 비교하는 것이다. 현재 자료는 그중 회귀 재현성과 일부 실패 개선을 입증한다.

## 8. IMU 드리프트는 어떻게 다루는가

### 8.1 자이로를 짧게 쓴다는 의미

gyro에 일정한 오차 `b`가 있다면, 단순화한 한 축의 각도 오차는 대략 `b·Δt`로 늘어난다. 예를 들어 **가상의** bias가 0.01rad/s이면 0.2초 동안은 약 0.002rad, 0.115°지만, 60초 동안 그대로 누적하면 약 34.4°가 된다. 이 숫자는 TRON IMU의 측정 bias가 아니라 시간 길이의 영향을 설명하는 예다.

이번 방법은 LiDAR가 수락될 때마다 기하 pose로 기준을 갱신하고, 다음 관측까지의 상대 회전만 초기값으로 쓴다. 그래서 장시간 gyro-only 자세를 절대 방향으로 사용하는 구조와 다르다.

그러나 이것은 **bias를 추정해 제거했다는 뜻이 아니다.** 관측이 틀리거나 오래 끊기면 누적 오차가 남는다. 반복 구조 때문에 GICP가 잘못된 자세를 계속 수락해도 오차가 생긴다. 중력 초기화 자체도 절대 yaw를 고정하지 못한다.

### 8.2 가속도를 위치 계산에서 뺀 이유

설치된 이번 코드에서 가속도는 초기 위쪽 방향을 얻는 데 쓰고, 위치는 점군 정합으로 얻는다. 가속도 오차를 장시간 두 번 적분하는 경로가 없다.

가상의 일정 가속도 오차 `0.1m/s²`를 외부 보정 없이 10초 동안 두 번 적분하면 위치 오차 항은 `0.5×0.1×10²=5m`다. 이 예는 실제 FAST-LIO가 그렇게 단순 적분만 한다는 뜻이 아니다. FAST-LIO에는 LiDAR 관측과 bias·중력 상태가 있고, 정상적인 융합을 통해 보정하려는 구조가 있다.

이번 선택은 IMU를 전부 신뢰하거나 전부 버리는 양자택일을 피한 것이다. **초기 중력과 단기 회전이라는 용도만 사용하고, 이동량은 점군에 맡겼다.** 그 용도가 이번 세 구간에 도움이 됐다는 증거가 있으며, 모든 주행 조건에 최적이라는 증거는 없다.

### 8.3 최근 ‘가만히 있어도 조금 회전’한 BAG과의 관계

진입점 BAG에서 연속 LiDAR yaw 변화는 약 -5.63°, wheel odometry는 약 +0.32°였다. 기존 측위·IMU 예측을 초기값으로 쓰지 않고 처음·끝 원본 점군 세 쌍을 직접 point-to-plane ICP로 맞추자 약 -5.57° / -5.68° / -5.68°가 나왔다. 각 쌍에 -10°·0°·+10° 초기값을 주어도 같은 해로 모였다. [H5]

이 결과는 **그 변화가 단순히 연속 gyro 적분만의 착시일 가능성을 낮추는 교차 확인**이다. 같은 LiDAR를 사용했으므로 외부 실측 정답은 아니며, 정지 환경과 고정된 센서 장착을 전제로 실제 방향 변화가 있었을 가능성이 높다는 해석이다.

여기서 쓴 point-to-plane ICP는 추가 진단 도구다. **기준 추적 알고리즘을 GICP에서 point-to-plane으로 다시 바꾼 것이 아니다.** 또한 이 BAG에는 명령 출력이 없어서 회전의 기계적 원인이나 실제 0 명령 여부까지 확정하지 못했다.

## 9. 이 선택은 일반적인가

### 9.1 설계 패턴 자체는 기존에 존재한다

정합 초기값에 운동 예측을 사용하는 것은 새로운 발상이 아니다. 공식 Open3D 설명도 초기 정렬을 입력으로 둔다. 공개된 `hdl_graph_slam`의 scan matching 구현은 선택적으로 IMU frontend 또는 robot odometry에서 얻은 상대 변환을 초기 추정에 결합하고 정합을 실행한다. 그 구조는 이번 ‘예측 후 정합’이라는 설계의 실제 선례다. 구현과 필터·지도 방식까지 동일하다는 뜻은 아니다. [hdl_graph_slam 원 구현](https://raw.githubusercontent.com/koide3/hdl_graph_slam/master/apps/scan_matching_odometry_nodelet.cpp)

가속도로 초기 중력 방향을 정하는 것도 로컬 FAST-LIO 초기화 코드에서 직접 확인할 수 있다. 따라서 ‘어떤 기하 평면을 바닥이라고 추측하기보다 관성 방향을 이용한다’는 선택 자체가 특이한 발명은 아니다. [C6]

### 9.2 이번 작업에서 시스템에 맞춘 부분

| 흔히 볼 수 있는 구성 원리 | 이번 시스템에서 정한 구체적 선택 |
|---|---|
| 운동 예측으로 정합 초기값 보조 | 평행 이동 예측 없이 gyro 회전만 사용 |
| 관성 방향으로 초기 중력 정렬 | 초기 ±0.5초 가속도 중앙값 |
| local map 기반 scan matching | 최근 수락 scan 15개, 20cm voxel |
| 관측 품질 검사 | fitness·예측 대비 위치/회전 보정 한계 |
| 시각과 유효성 관리 | 실패 pose를 최신 측정으로 쓰지 않고 geometry 유효성 분리 |
| 비싼 정합과 제어 루프 분리 | 기존 Supervisor 내부의 별도 계산 worker와 epoch 처리 |

첫 열은 기존 구현에서 확인되는 설계 원리다. 두 번째 열의 숫자는 이 프로젝트에서 사용·회귀 검증한 기준값이며 업계 공통 표준은 아니다. ‘일반적’이라는 답변은 채택 비율을 조사했다는 뜻도 아니다.

### 9.3 왜 곧바로 알고리즘을 통째로 바꾸지 않았나

남아 있는 변경 기록에서 확인되는 선택은 기존 GICP와 주요 수치를 보존한 채, 구체적인 결함을 고치는 쪽이었다. 이 방식은 개선이 새 엔진 때문인지, 입력·예측·출력 문제 수정 때문인지 비교하기 쉽고 기존 구조 변경도 작다.

처음부터 다른 SLAM 전체를 넣었다면 결과가 좋아져도 무엇이 원인이었는지 분리하기 어려워진다. 이는 최소 수정이라는 프로젝트 요구와도 맞는다. 다만 ‘작게 고쳤기 때문에 반드시 최선’은 아니다. 관측 퇴화·고속 왜곡·장거리 드리프트가 남는다면 이후 더 넓은 측위 시스템을 검토할 수 있다.

### 10.1 최종 설치 버전의 회귀 결과

|---|---|---:|---:|---:|---:|---:|

`102101`의 RMSE 중앙값은 소폭 증가했다. 그러므로 ‘모든 오차 지표가 줄었다’고 설명하지 않는다. 여기서 핵심적으로 나아진 것은 긴 추적 중단이 없어진 것과, 두 정상 확인 구간의 상대 회전을 추적한 것이다.

`103313`의 최종 방향을 180°로 맞추기 위해 결과를 바꾸지 않았다. 그 기록에는 반대 방향 회전도 있어, 다른 BAG의 예상 각도를 정답으로 강제할 수 없다.

### 10.2 fitness 1.0은 정확도 100%가 아니다

Open3D 0.18.0의 실제 `Registration.cpp`는 대응점 수를 source 점 수로 나눠 fitness를 계산한다. `inlier_rmse`는 선택된 대응점 사이 거리의 제곱 평균 제곱근이다. 따라서 fitness 1.0은 설정된 대응 거리 안에서 source 점마다 대응을 찾았다는 뜻이지, 로봇 위치가 100% 정확하다는 뜻이 아니다. 이 설명은 일반 문구보다 **사용한 버전의 실제 구현**을 기준으로 했다. [Open3D 0.18.0 결과 계산 코드](https://raw.githubusercontent.com/isl-org/Open3D/v0.18.0/cpp/open3d/pipelines/registration/Registration.cpp)

반복되는 벽·계단에서는 다른 위치의 비슷한 표면에도 대응점이 생길 수 있다. GICP 내부의 표면 공분산을 사용한 최적화 목적과, 보고서에 표시한 대응점 거리 RMSE도 같은 개념으로 혼용하지 않는다.

### 10.3 RMSE 8cm는 로봇 위치 오차 8cm가 아니다

표의 RMSE는 각 프레임 정합의 **점 대응 잔차**다. 표의 중앙값·P95는 그 프레임별 RMSE를 분석 구간 전체 시도에 대해 집계한 값이다.

위치 추정이 실제로 몇 cm 틀렸는지를 알려면 추적기와 독립적인 로봇 위치·자세 정답이 있어야 한다. 이 기록에는 그 정답이 없다. wheel odometry는 계단에서 별도 오차를 가질 수 있고, gyro는 이미 이번 추적의 입력이므로 둘 중 하나와 일치한다고 독립 정확도 검증이 끝나는 것도 아니다.

### 10.4 최신 재계산은 ‘보존 확인’이다

후속 오프라인 검증에서 원본 세 BAG의 1,307프레임을 다시 처리했을 때 상태·시각 불일치는 0이었고, 기존 기준 궤적과의 최대 위치 수치 차이는 1.69×10⁻¹⁰m 미만이었다. 이는 같은 알고리즘을 옮기고 실행해도 기준 결과가 유지된다는 회귀 증거다. **실제 로봇의 위치 오차가 그 정도로 작다는 뜻은 전혀 아니다.** [H4]

현재 PC의 진입점 BAG 1배속 재생에서는 새 유효 결과의 관측 지연이 중앙값 0.181초, P95 0.203초, 최대 0.341초였다. 유효 표본 93개, 점군 유실·IMU 거부·worker 오류 0이었다. 로봇 통신·실기 진동·최악의 모든 제어 주기 지연까지 검증한 값은 아니다.

## 11. RViz에서 좋아 보인 것 중 무엇이 실제 알고리즘 개선인가

| 화면에서 보인 변화 | 원인 계층 | 무엇을 의미하는가 |
|---|---|---|
| 높이 방향과 주변 구조가 덜 뒤집힘 | 초기 좌표계 | 중력 기준 초기화의 효과 |
| 계단참을 돌아 반대 방향으로 이어짐 | 예측·기하 정합 | 회전 중 추적 갱신의 연속성 개선 |
| 거절 구간이 정상 궤적처럼 이어지지 않음 | 유효성·출력 | 모르는 위치를 아는 것처럼 그리지 않음 |
| 비교 경로의 겹침이 달라짐 | 시각·원점·몸체 변환 | 비교 기준 정렬 효과; 곧바로 추적 정확도 개선으로 세면 안 됨 |
| `FINAL_ARRIVAL` 표시가 나중으로 이동 | 영상 annotation | 수동 표시 시각 수정; 추적 계산이나 실제 도착 검출 변경 아님 |

초기 조사에서는 header 시각·공통 기준 시각·센서 원점을 맞춘 비교 함수를 별도로 검토했다. 그러나 기존 wheel/FAST-LIO 비교 builder의 모든 경로가 엄밀한 공통 몸체 기준으로 재구현됐다고 일반화하면 안 된다. 당시 문서에도 개별 시작 자세·bag 기록 시각을 쓰는 비교의 한계를 남겼다. 수치 표에서 동일한 LiDAR header 목록을 확인한 것과, 모든 RViz 색상의 절대 오차 비교가 유효한 것은 다른 조건이다. [H1, H2]

사용자가 지적한 ‘2~3단 남기고 도착’은 RViz의 `FINAL_ARRIVAL` 표시였다. 조사 결과 그것은 사람이 지정한 영상 시각에 가까운 LiDAR pose를 연결한 annotation이었고, 실제 Stair Supervisor가 내린 도착 판정이 아니었다. 후속 작업에서 표시 시각을 수정하고 수동 표식임을 명시했지만 **녹색 추적 계산은 보존했다.** [H3]

따라서 이 자료에서는 다음 두 주장만 분리해서 할 수 있다. **상대 측위가 더 일관되게 계산됐다**는 것은 추적 기록의 근거가 있다. **로봇 몸체가 마지막 단을 완전히 벗어났다는 자동 판단이 완성됐다**는 것은 그 표시로 입증할 수 없다.

## 12. 원래 비교 도구에서 실제 Supervisor로 옮길 때 달라진 것

### 12.1 같은 수학을 사용해도 실행 조건은 달라진다

원래 비교 도구는 파일을 순차 처리하며 CSV·BAG을 만들어 냈다. 실제 노드는 센서가 들어오는 동안 명령과 상태를 계속 처리해야 한다. 계산 때문에 명령 갱신이 멈추거나, 오래 걸린 결과가 최신 pose처럼 도착하면 곤란하다.

그래서 후속 구현은 기존 Supervisor 안에서 추적 계산을 별도 worker process로 수행하고, 센서 콜백은 유한 크기의 입력 버퍼에 전달하도록 구성했다. ROS 운영 노드를 하나 더 추가한 것과는 다르지만, OS 계산 프로세스는 별도로 존재한다. [C8]

측정 시각, 수신 시각, 계산 완료 시각, 마지막 유효 geometry 시각을 나눠 기록한다. 프로세스 reset에는 epoch를 사용해 reset 이전 계산 결과나 진입 anchor가 새 실행에 섞이지 않게 한다. 정합이 잠시 늦는 것과 실제 센서 단절도 제어 정책에서 구분할 수 있도록 상태를 제공한다.

### 12.2 측위와 제어의 연결은 별도 검증이다

추적기는 “현재 센서가 여기 있다”를 제공한다. Supervisor는 그 위치를 몸체 기준과 계단 경로 기준으로 옮긴 뒤 “중심선보다 왼쪽인가”, “계단참에 몸체가 들어왔는가”, “다음 계단을 향하는가”를 판단해야 한다.

```text
센서 pose 추정
  → 몸체 pose로 변환
  → 계단 경로 좌표로 변환
  → 횡방향·방향·진행 오차 계산
  → 명령 계산
  → 실제 로봇 응답
  → 다시 센서로 관측
```

마지막 단계까지 연결돼야 폐루프 주행이다. BAG은 이미 기록된 로봇 움직임이므로, 우리가 나중에 계산한 보정 명령에 맞춰 과거 로봇이 새로 움직이지 않는다. BAG으로 보정 부호나 제약 발동은 검사할 수 있지만, 그 명령을 보냈을 때 실제로 중심이 유지되는지는 별도다.

후속 오프라인 제어 평가에서는 두 시각 확인 BAG의 첫 4초는 후보 제약 안에 있었으나, 더 진행하면 13.80초·22.80초에 경계 제약에 걸렸다. 이는 **좋아진 측위를 보존한 상태에서도 제어 경로의 좌표·구간 전환 조건이 맞지 않을 수 있음을 보여 준다.** 추적 개선의 실패로 단정하거나, 반대로 모든 제어 조건을 풀어야 한다는 결론으로 확대하지 않는다. [H4]

### 12.3 문서 작성 시점의 적용 상태

- 녹색 추적 기준 버전은 비교 도구에 적용·보존돼 있다.
- 같은 추적 핵심을 쓰는 Supervisor용 구현과 원본 BAG 회귀 결과도 존재한다.
- 직전 작업의 단일 구간 시험 추가 수정과 후보 경로는 오프라인 검증용 별도 사본이며 운영 설정에 배포하지 않았다.
- TRON은 사용자 설명상 꺼져 있다. 이 문서 작성에서 로봇 연결·주행·설정 변경은 하지 않았다.

과거 보고서의 ‘Supervisor 미연동’은 당시 작업 상태다. 현재는 연동 코드가 있으나 **실기 전체 층간 주행 완료가 검증된 상태는 아니다.** 시점이 다른 문장의 의미를 합쳐 “처음부터 전부 구현됐다”거나 “지금도 비교 도구밖에 없다”고 설명하지 않는다.

## 13. 아직 구현하지 않았거나 입증하지 못한 것

| 항목 | 현재 상태 | 왜 중요한가 |
|---|---|---|
| 점별 deskew | 이번 추적기에는 없음 | 한 packet 안에서 회전·이동하면 점마다 촬영 자세가 다를 수 있음 |
| gyro bias·온도 보정 | 없음 | 짧은 적분에도 오차가 있고 유실 시간이 길면 영향 증가 |
| IMU 가속도 기반 위치·속도 상태 | 사용하지 않음 | 관측이 빈약한 구간에서 관성 이동 예측의 도움을 받지 못함 |
| 시간 offset 온라인 추정 | 없음 | header를 쓴다는 것만으로 두 센서 시계가 물리적으로 동기화됐다고 보증하지 않음 |
| LiDAR–IMU 이동 성분의 동역학적 보상 | 이번 예측에는 없음 | 회전축과 센서 위치가 다를 때 더 완전한 운동 모델에는 영향 |
| 초기 정지 상태 인증 | 완성된 검출기 없음 | 초기 가속도 중앙값에 동적 가속도가 섞일 가능성 |
| 기하 퇴화 탐지 | 별도 Hessian/관측가능성 분석 없음 | 비슷한 벽·계단에서 내부 점수는 좋지만 특정 방향 위치가 불확실할 수 있음 |
| 전역 재측위·loop closure | 없음 | 큰 유실 또는 장거리 누적 오차를 자동으로 되돌리는 시스템이 아님 |
| absolute building/floor pose | 외부 anchor 필요 | local 좌표만으로 층 번호나 건물 지도 위치를 알 수 없음 |
| 실제 몸체 위치 정확도 | 외부 실측 정답 없음 | cm 단위 정확도·최악 오차를 인증할 수 없음 |
| 실제 주행·균형·대기 성능 | UNVERIFIED | 위치를 아는 것과 구동계가 원하는 힘/속도로 반응하는 것은 다름 |

이 목록은 알고리즘을 당장 전부 확장하라는 뜻이 아니다. **이번 개선으로 무엇을 얻었고 무엇은 얻지 않았는지 명확히 하기 위한 경계**다. 예를 들어 deskew는 필요성이 확인됐을 때 기준 BAG 회귀와 별도 실제 오차 평가를 거쳐 추가해야 하며, 이름만 고급스러운 기능을 넣는다고 자동으로 나아지지 않는다.

특히 ‘예측된 변환이 있다’와 ‘현재 측정이 유효하다’를 계속 분리해야 한다. 장시간 관측이 없는데 예측값을 계속 발행하면 화면은 부드러워질 수 있어도, 이번에 고친 오래된 위치의 최신 측정 위장 문제가 다른 형태로 돌아온다.

## 14. 구현을 이해하기 위한 의사코드

아래는 흐름을 설명하기 위한 축약이다. 실제 ROS 실행 스크립트나 완전한 예외 처리가 아니다.

```python
# 최초에 준비: 회전 보정, 설정, 빈 local map
R_lidar_imu = inverse(configured_R_imu_lidar)
last_accepted_pose = None
last_accepted_stamp = None

for scan in selected_lidar_packets:
    t = scan.header_stamp
    points = filter_and_voxelize(scan.xyz)

    if last_accepted_pose is None:
        # streaming에서는 필요한 표본이 실제 도착해야 진행
        up = median_acceleration_in_lidar_axes(t - 0.5, t + 0.5)
        pose = align_up_to_world_Z(up)
        save_initial_scan(pose, points)
        publish_status("BOOTSTRAP", geometry_valid=False)
        last_accepted_pose, last_accepted_stamp = pose, t
        continue

    prediction = copy(last_accepted_pose)
    if imu_interval_is_supported(last_accepted_stamp, t):
        prediction.rotation *= relative_gyro_rotation(last_accepted_stamp, t)
    # 지원되지 않으면 마지막 관측 자세를 초기값으로 기하 복구 시도

    candidate = GICP(points, recent_accepted_map, initial=prediction)
    correction = inverse(prediction) @ candidate.pose

    if accepted_by_fitness_and_innovation(candidate, correction):
        last_accepted_pose = candidate.pose
        last_accepted_stamp = t
        add_scan_to_local_map(candidate.pose, points)
        publish_valid_measurement(candidate.pose, measured_at=t)
    else:
        publish_invalid_status(reason=candidate.reason)
        # 새 유효 odometry를 만들지 않고 지도도 갱신하지 않음
```

실제 코드는 빈 점군, IMU 표본 수·순서·공백, 행렬 유효성, 초기화 지원, worker reset 등을 추가로 처리한다. 오프라인 도구와 스트리밍 코드의 초기화 출력·상태 이름 차이는 앞 절의 설명을 따른다.

## 15. 향후 수정할 때 보존해야 할 검증 기준

1. **같은 입력 프레임인가:** 기존·수정 결과의 header 시각 목록을 먼저 비교한다. 잘 된 부분만 다르게 잘라 놓고 개선율을 계산하지 않는다.
2. **같은 좌표 기준인가:** 센서/몸체 원점, IMU 회전 방향, local map과 stair profile anchor를 구분한다. 중력 방향까지 임의로 없애지 않는다.
3. **회전이 실제로 추적되는가:** 고정된 세계 좌표 회전으로 그림을 바로 세운 효과와 시간에 따른 상대 회전 추적을 구분한다.
4. **실패가 보이는가:** 강제 거절·IMU 누락·worker reset 후 오래된 pose가 새 유효 측정으로 발행되지 않는지 검사한다.
5. **복구가 되는가:** 기하 갱신이 재수락되면 새 시각에서 gyro 예측을 재개하는지 확인한다. 실패를 영구 latch로 바꾸지 않는다.
6. **정확도 기준이 독립적인가:** 내부 fitness, 수락률, 입력 gyro, 동일 알고리즘 재계산만으로 실제 위치 정확도를 주장하지 않는다.
7. **제어 시험인가, 기록 평가인가:** 기록 궤적에 가상 명령을 계산하는 작업과 명령에 반응하는 실기 폐루프를 구분한다.
8. **기준 버전과 비교 가능한가:** 현재 보존한 추적 핵심·보정 파일·spec·의존성 해시와 변경점을 기록한다.

이번 문서의 결론은 **검증 가능한 초기화·회전 예측·유효성 처리로 기존 GICP의 추적을 개선했다**는 것이다. 이 결과를 가장 잘 보존하는 방법도 이름이 다른 알고리즘을 계속 바꾸는 것이 아니라, 위 계약과 수치가 유지되는지 확인하면서 남은 경로·제어 문제를 따로 해결하는 것이다.
