## 변경

- `photo_tour.yaml`: 남서→북서→남서→남동→옥상 탈출점. 남서 재방문도 별도 촬영·메일. 옥상 탈출점에서 대기하며 자동 하강은 하지 않는다.
- UI의 순회 순서 표시를 동일하게 변경했다. 촬영 도착 허용값60cm/±50°는 유지한다.
- NAV의 기존 단일 재시도 전에 최신 map→base_Link TF를 기다린다. 최대30초, TF age0~0.5초가 연속0.5초 유지되어야 재시도한다. 기존 목표가 종료된 뒤에만 대기하며 새 목표를 겹쳐 보내지 않는다. 정지 요청이 오면 재시도를 하지 않는다. 회복되지 않으면 NAV_TF_RECOVERY_TIMEOUT을 보고한다. TF 허용값을 늘리거나 오래된 위치로 성공 처리하지 않는다.
- 회복 뒤 지도 세대·층·제어 상태를 다시 확인한 뒤 costmap을 갱신하고 동일 목표를 한 번 재전송한다. 반복 장애를 무한 재시도하지 않는다.
- 옥상 전용 순회는 기존 Stair Supervisor의 새 서비스로 WALK 전환을 요청한다. 별도 노드나 WebSocket 연결은 만들지 않는다. 기존 단일 제어 연결이 WALK 명령을 한 번 전송한 뒤 로봇 ACK나 모드 상태 응답을 기다리지 않고 NAV를 시작한다. 전송 실패는 응답 누락과 구분한다. 로컬 서비스 응답 대기도 제한한다. 정상 NAV 소유 상태에서 실제 로봇 모드가 STAIR로 남았을 때 이를 바로잡는 기능이며, 실행 중 계단 임무를 강제로 중단하는 기능은 아니다.

## 검증 및 한계

임무 회귀652개, 계단 회귀438개 통과. 응답 시간 제한과 회복 후 재확인을 보완한 최종 관련 회귀299개 통과. UI JavaScript 구문 검사 통과. 모의 테스트에는13.7초 입력 장애 뒤 회복, 일회성 최신 샘플, 지속 장애, 대기 중 취소, WALK 실패 시 NAV 미전송, 방문별 촬영이 포함된다.

`sip` 검토에서 서비스 응답 무기한 대기 가능성을 발견해 기존 bounded caller를 사용했다. 옥상 순회 시작용 WALK는 별도 단발 전송이며 기존 계단 모드 전환의 응답 확인 정책은 바꾸지 않는다. `ssotize` 읽기 검토 범위는 순회 YAML·UI·방문별 테스트이며 서로 일치한다. `mandela` 관점에서 모의 테스트는 무선망 및 실주행 성공률의 독립 검증이 아니다. 실제 성공 여부는 새 주행 BAG로 확인해야 한다. ROS의 오래된 TF 거절 동작은 보관된 Noetic upstream `costmap_2d_ros.cpp`의 getRobotPose 구현과 실제 오류 로그를 대조했다.

자료: `bag-analysis.txt`, `timing.json`, `mission-tests-final.log`, `stair-tests-final.log`, `focused-final.log`. 기존 BAG와 사용자 변경은 보존했다. 이번 작업이 요청하지 않은 주행·문 열기·메일 발송을 시작하지 않았다.

최종 사용자 지시에 따라 WALK 무응답도 NAV를 막지 않도록 수정했다. 실제 transport와 가짜 WebSocket을 연결한 테스트에서 WALK 응답을 전혀 공급하지 않아도 후속 전진 명령 전송, 미처리 응답 예약0개, WALK 단발 전송을 확인했다. 전송 자체 오류는 별도로 실패한다.
