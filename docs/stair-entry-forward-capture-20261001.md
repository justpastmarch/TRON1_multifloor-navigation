# 계단 진입 정렬 대기 수정 · 2026-10-01

수정 대상은 첫 상승 전 ALIGN 진입 허용각이다. 기존 FSM, ROS 노드, 계단참 회전, 상승·도착 판정, 측위 알고리즘을 유지한다. 원래 저장소에 반영하고 기존 스택을 재시작해 v16 적용을 확인했다. 실제 주행은 UI에서 사용자가 녹화를 포함한 테스트를 시작하는 방식이다.

## 원인과 근거

**OBSERVED:** `ui_test_20261001_215526_dc7fa299.bag`에서 NAV는 21:55:40.632에 성공했다. 이후 VERIFY_ENTRY를 거쳐 ALIGN에 진입했고, 기록된 ALIGN 진단 238개는 약 23.697초에 걸쳐 모두 방향 조건을 통과하지 못했다. 방향 오차는 10.34~13.89도, 기존 허용각은 10도였다. 차체 영역·높이·진입 확인 조건은 모두 통과했다. ALIGN 진입 후 전송된 twist 663개의 전진 입력은 모두 0이었다. 같은 구간 조이스틱 비중립 입력은 없었다.

**OBSERVED:** BAG에 21:56:06.585 미션 취소 요청이 있다. 취소 전 ALIGN 진단은 TRACKED이며 loss_response=false였다. 취소 이후의 first_fault 메시지는 실제 상승 실패 원인의 증거로 사용하지 않는다.

**사용자 관찰:** 양 바퀴가 첫 단에 닿으며 실제로 계단과 평행해졌다. **UNVERIFIED:** 접촉이 정렬을 방해했는지, 로봇이 실제로 몇 도 틀어졌는지는 외부 기준으로 측정되지 않았다. LiDAR odom과 바퀴 odom의 해당 구간 회전 변화 부호도 다르다. 저장된 경로 방향, 측위 오차, 명령 응답 중 어느 쪽이 그 차이를 만든 것인지 확정하지 않았다.

Finding: 작은 추정 방향 오차를 해소할 때까지 전진을 0으로 고정하는 ALIGN이 첫 상승 진입을 막았다. **Safety: S2 / Mobility: M4.** 코드 근거: `src/stair_supervisor/src/stair_supervisor/stair_feedback.py`의 corridor_entry 및 ALIGN completion_checks.

## 최소 변경

두 운영 경로 `stair_3f_4f_up`, `stair_5f_rf_up`의 `entry_corridor_yaw`를 10도에서 **20도(0.3490658503988659 rad)**로 조정한다. 제어 정책 표시는 `2026-10-01-entry-capture-v16`이다. 동작 변경은 이 진입 허용각 조정이며, 정책 문자열은 실행 버전 확인용이다.

기존 코드가 차체 영역·높이·진입 확인·새 관측 조건을 만족한 ALIGN을 완료하면 FORWARD_SEGMENT_1으로 넘어간다. 기존 상승 제어가 가속도 제한과 경로 검사를 거쳐 전진 및 제한된 조향을 요청한다. 20도를 넘으면 기존 제자리 정렬이 유지된다. 따라서 정렬 게이트 전체를 없애거나 예상 경로 검사 전체를 비활성화한 수정은 아니다.

20도는 이번 10~14도 정체를 해소하기 위한 **TUNE** 값이다. 최대 안전 진입각이나 통계적 오차 상한을 실측한 값이 아니다. 방향 오차 20도 이내만으로 상승이 허가되지 않으며, 기존 차체 경계·높이·데이터 유효성·상승 경로 조건이 계속 적용된다. 이 값이 실제 주행의 최적값인지는 **UNVERIFIED**다.

일반적인 첫 상승 요청은 기존 내부 입력 상한 0.55이며 WebSocket 전진 입력 1에 대응한다. 첫 출력부터 즉시 1을 보내는 변경은 아니다. 가속도 제한 0.15와 기존 경로 검사가 출력에 적용된다. 계단참 속도, 최대 조향, 두 번째·세 번째 상승 진입각, 마지막 단 높이 판정은 조정 대상이 아니다.

## 검증의 범위

실패 BAG의 최초·최종 ALIGN 관측에서 기존 10도의 대기와 수정값에서의 ALIGN 완료·양수 전진 출력을 확인했다. 별도 행동 검증은 20도 경계와 바로 바깥 각도, 큰 방향 오차, 높이·측면 이탈, 동일 프레임·측위 지연을 포함한다. 관련 회귀 검사 170개가 통과했다. 전체 ALIGN 기록 238개를 비교하면 기존 설정은 완료 가능 관측 0개, 수정 설정은 첫 중복 프레임을 제외한 237개다. 새로운 물리 궤적을 예측한 결과는 아니다.

**mandela 검토:** 기록된 추정 pose를 입력하고 제어기의 출력으로 판정하는 검증은 소프트웨어 조건 검증이다. 실제 자세·완주를 독립적으로 검증하지 못하며, 같은 BAG에 맞춰 조정했으므로 독립 평가 자료도 아니다. 수정 출력으로 과거 BAG의 물리 경로가 바뀌었다고 가정하지 않는다. 실제 효과는 새 주행의 영상·운전자 관찰·BAG으로 구분하여 판정한다.

실주행 확인 순서: NAV → VERIFY_ENTRY → ALIGN 통과 → 첫 상승 전진 입력 → 계단참 → 회전 → 두 번째 상승 → RF 우측 회전·추가 두 단 → 도착. 중단 시 최초 원인과 후속 취소 메시지를 분리한다. 정렬만 해소되고 다음 단계에서 멈추면 해당 결과를 별도 원인으로 기록한다.

소프트웨어 검증·배포·실행 상태의 최종 기록은 분석 폴더의 `verification.json`과 로그에 저장한다. 설정 검사에서 configured=true를 확인했고, 재시작한 runtime에서 v16·5F READY·supervisor NAV·로봇 연결을 확인했다. 실제 미션은 시작하지 않았으며 실주행 성공을 주장하지 않는다.

검사에서 `_entry_verified=True`는 이미 통과한 진입 확인을 재현하기 위한 주입이다. 반복한 고정 pose·새 프레임 검사는 제어 출력 검사이며 로봇이 이동했다는 뜻이 아니다. 최초·최종 기록 pose의 단위 검사는 yaw와 위치를 사용하고, 전체 ALIGN 관측의 비교 재생은 기록된 roll·pitch도 사용한다. 비교 재생은 gyro 원시 데이터 또는 실제 WebSocket 응답을 재생하지 않는다.

이 문서의 S2는 경계 대응을 오판할 가능성을 검토해야 하는 수준이며 사고 관측을 뜻하지 않는다. M4는 계단 상승 진입을 막아 임무를 수행하지 못하는 수준이다. 물리 위험도를 실측한 점수가 아니다.

운영 저장소의 검사를 재현하려면 해당 저장소에서 ROS 및 devel 환경을 읽고 config.env를 읽은 뒤 `ROS_MASTER_URI=http://127.0.0.1:11991`, `ROS_IP=127.0.0.1`, `PYTHONDONTWRITEBYTECODE=1`을 설정한다. `$STAIR_PYTHON ./src/stair_supervisor/test/test_entry_forward_capture.py`로 추가 행동 검사를 실행한다. 이 테스트는 같은 저장소의 운영 경로 설정·프로파일·기존 테스트 도우미를 사용한다. 다른 설치 환경에 그대로 이식 가능한 검사라고 주장하지 않는다.

## 기록과 복구

원본 BAG는 `/mnt/ethan/tron-bags/live/ui-tests/ui_test_20261001_215526_dc7fa299.bag`이다. 감사/분석 폴더는 작업공간의 `entry-forward-capture-20261001/`이며 변경 전 사본, 해시, Git 상태, 검사 코드·결과를 보존한다. 기존 worktree 변경을 되돌리지 않고 지정 파일의 기존 내용을 확인한 뒤 적용한다. 커밋·푸시는 수행하지 않는다.

새 주행에서 제자리 정렬 대기가 이어지는 경우 UI 진단의 incomplete_conditions, 각도, 차체 경계를 함께 확인한다. 주행 중단 뒤 조종기로 제어를 회수할 수 있다는 기존 운용 조건을 유지한다. 0 명령은 물리적 위치 유지의 증거가 아니다. 이전 설정으로 복구할 필요가 생기면 전체 worktree를 되돌리지 않고 해당 두 entry_corridor_yaw 값만 변경한다.

Safety verdict: **UNVERIFIED — 확대 진입각의 실제 계단 응답 검증 필요.** Mobility verdict: **소프트웨어상 기록된 ALIGN 정체 해소를 검사하며, 실제 완주 개선은 UNVERIFIED.**
