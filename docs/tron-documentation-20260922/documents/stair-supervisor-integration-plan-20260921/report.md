# 검증한 LiDAR 측위를 기존 Stair Supervisor에 연결하는 구현 계획

**제안: 녹색 경로를 만든 측위 계산은 보존하고, 기존 Supervisor 내부에 실시간 입력 처리와 위치·방향 피드백을 연결한다. 기본안의 새 ROS 노드는 0개다. 이번 작업은 계획과 읽기 전용 호환성 확인이며, 운용 코드·기체 설정·주행 명령은 변경하지 않았다.**

첫 적용 범위는 사용자 확인이 있는 **3F→4F 상행의 진입·첫 구간·계단참 회전·둘째 구간·출구 확인**이다. 하행과 5F↔RF는 같은 코드 기반을 사용하되 별도 경로·문 동작·실주행 검증을 거친다. 사용자가 확인한 `FINAL_ARRIVAL` 문제는 수동 RViz 표시였으며 실제 Supervisor 결함의 증거로 사용하지 않는다.

OBSERVED는 코드·기록·실행에서 직접 확인한 사실, INFERRED는 그 근거에서 도출한 판단, UNVERIFIED는 아직 검증하지 않은 조건이다. 아래 구현·수락 기준은 **제안**이며, 이미 구현됐거나 실주행을 통과했다는 뜻이 아니다.

## 3\. 실시간화: 같은 계산에 도착한 센서만 공급

제안 데이터 흐름은 다음과 같다.

`/livox/lidar + /livox/imu → 기존 Supervisor의 수신 버퍼 → 측위 worker → 유효 관측 snapshot → evidence·피드백 → 기존 RobotTransport`

1.  **동결 core를 패키지 안으로 편입한다.** `registration_core.py`의 계산을 `stair_supervisor/lidar_tracking_core.py`로 그대로 편입하고 최초 내용 해시를 비교한다. 새 실시간 어댑터와 새 재생 검증기는 이 한 모듈을 함께 사용한다. 기존 오프라인 도구·기준 사본은 과거 비교 자료로 보존한다.
2.  **IMU는 시간 순서의 제한된 버퍼로 받는다.** IMU header와 LiDAR header를 사용하며 수신 시각·처리 완료 시각은 따로 기록한다. LiDAR 시각을 보간하는 데 필요한 IMU 표본이 실제 도착한 후 계산한다. 나중에 도착한 데이터를 미리 읽은 것처럼 처리하지 않는다.
3.  **초기 ±0.5초 계산을 보존한다.** 진입 준비 중 필요한 구간을 수집하고, 초기화가 끝난 뒤 현재 시각에 충분히 가까운 기하 관측이 생기면 제어를 연결한다. 초기 pose의 원래 시각을 최신 시각으로 바꾸지 않는다. 매 계단·매 phase마다 이 초기화를 반복하지 않는다. 실제 초기 구간이 저동적 상태인지도 기록한다.
4.  **이후에는 과거 수락 지도에 현재 scan을 맞춘다.** 매 두 번째 LiDAR packet이라는 기본 선택과 15개 scan 지도를 유지한다. 계단참 회전 때 지도·누적 회전을 초기화하지 않는다. 전체 누적 점군 저장·시각화는 실시간 제어 경로에서 분리한다. 이는 현재 위치 계산에 쓰이는 local map을 바꾸는 작업이 아니다.
5.  **callback과 명령 송신에서 GICP를 실행하지 않는다.** 동일 Supervisor의 worker가 계산하고, 제어 쪽은 짧은 lock으로 완성된 불변 snapshot만 읽는다. 지연된 옛 scan을 무제한 쌓지 않는다. backlog가 생기면 결손 수와 마지막 실제 관측 나이를 남기며, 이를 새 측위로 포장하지 않는다.
6.  **epoch를 연결한다.** snapshot에 `tracking_epoch`, 실행 ID, 시각을 붙인다. 재초기화·취소·새 실행 후 늦게 나온 이전 계산은 제어에 사용하지 않는다. 복구로 pose 기준이 바뀌면 과거 목표선과 조용히 섞지 않고 다시 연결한 뒤 진행한다.

**OBSERVED:** 현재 오프라인 초기화는 미래 0.5초를 포함하며, IMU 전체를 먼저 읽는다. 반면 scan 정합 지도는 이전 수락 scan으로 구성된다. [현재 처리](/home/m3tron/Desktop/TRON1_Modular_Navigation/tools/offline_lio/process_bag.py#L165), [초기화·예측](/home/m3tron/Desktop/TRON1_Modular_Navigation/tools/offline_lio/registration_core.py#L138). **INFERRED:** 수학을 유지한 순차 처리 이식이 가능하다. **UNVERIFIED:** 현재/탑재 PC에서 요구 지연 내 계산되는지.

worker thread만으로 송신 주기를 지킬 수 있다는 보장은 하지 않는다. 기존 40Hz 송신의 지연을 함께 측정한다. CPU 또는 라이브러리 간섭으로 실패하면 내부 worker 분리 방안을 비용·통신 계약과 함께 먼저 보고한다. 이 계획만으로 새 ROS 노드를 추가하는 것으로 간주하지 않는다.

## 4\. Supervisor의 관측 계약

새 내부 `TrackingSample`은 다음을 보관한다. 공개 action/msg 구조는 첫 묶음에서 유지한다.

| 항목                                              | 의미                               |
| ----------------------------------------------- | -------------------------------- |
| 측정 시각·수신 시각·완료 시각·마지막 기하 관측 시각                  | 센서 지연과 계산 지연, 실제 위치의 나이를 구분      |
| `T_stair_lidar`, `T_stair_base`, roll/pitch/yaw | 센서 자세와 기체 자세를 구분                 |
| `geometry_valid`, 상태, 거절 이유                     | BOOTSTRAP·회전 예측·실제 정합을 구분        |
| fitness·RMSE·예측 대비 보정량                          | 정합 내부 진단. 실제 위치 오차의 정답으로 사용하지 않음 |
| epoch·sequence·원본 calibration hash              | 실행 교체·중복 입력·장착값 변경 추적            |

`T_A_B`를 B 좌표를 A 좌표로 옮기는 변환으로 정의하면, `T_stair_base = T_stair_lidar × inverse(T_base_lidar)`다. FAST-LIO YAML의 **LiDAR↔IMU 회전**과 **기체↔LiDAR 장착 변환**은 별개다. 장착 translation을 임의로 0으로 확정하지 않는다.

STAIR 내부의 연속 상대 좌표계를 사용한다. 기존 `odom→base_Link`나 `map→odom`의 새 발행자가 되지 않는다. 지도·층 변경 때문에 계단 중 local pose가 재설정되지 않게 한다. 바퀴 odom은 비교 진단으로 보존하고, 실행 도중 LiDAR에서 바퀴 pose로 자동 교체해 위치가 뛰게 만들지 않는다. `off/observe/control` 모드는 실행 시작 전에 선택한다.

**매 실행의 계단 기하 연결:** profile 좌표 `P`는 실측한 진입 기준점과 첫 구간 중심선으로 정하고, 기준 점군/벽·첫 단 모서리 대응을 저장한다. 실행마다 `T_P_base(entry)`를 구한다. 첫 현장 검증에서는 표시한 진입 위치·방향의 외부 측정으로 이를 제공하고, 자동 운용에서는 중력 정렬한 진입 점군에서 기준 벽·모서리 대응을 맞춰 SE(2) 변환을 구한다. 사용한 기하가 평면 위치와 yaw를 모두 구속하는지 검사한다. 점/벽의 개수를 일률적인 진입 gate로 정하지 않고, 해당 계단의 대칭 후보를 구별할 수 있는 대응을 사용한다. NAV/AMCL pose는 초기 후보로만 쓰고, 대칭 후보가 남거나 한 방향이 관측되지 않으면 해당 계단 진입을 확정하지 않는다.

`RouteAnchor`의 단일 소유자는 `stair_feedback.py`이며, `T_stair_P = T_stair_base(entry) × inverse(T_P_base(entry))`로 목표선·계단참·출구 경계를 같은 frame에 옮긴다. 원래 profile은 변경하지 않고 변환·근거·불확실성·epoch를 snapshot으로 저장한다. 반복 정합 잔차만으로 불확실성을 확정하지 않고, 다른 진입 위치·방향의 외부 측정과 비교해 최대 오차를 정한다. 그 오차와 장착 오차를 포함한 여유가 통로 안에 남아야 제어를 허용한다. 실행 중 목표선을 현재 로봇 위치에 따라 계속 이동시키지 않는다.

측위 재초기화로 frame이 바뀌면 RouteAnchor도 무효화한다. 정지/지지 가능한 위치에서 같은 기준 기하로 다시 연결하고, 새 변환과 과거 물리 목표가 일치한다고 확인한 뒤 재개한다. 확인할 수 없으면 제어 재개 대신 운전자 인계 상태로 남긴다. 이는 기존 초기 위치 오인 문제를 새 local frame 안에 숨기지 않기 위한 연결 계약이다. 구현 동등성 시험에는 수학적 좌표 변환을, 현장 시험에는 서로 다른 진입 위치·방향에서의 실제 정렬을 포함한다.

0.12초를 단순히 더 큰 한 숫자로 바꾸지 않는다. `sensor_interval`, `geometry_age`, `transport_delay`, `compute_time`, `clock_uncertainty`를 분리한다. 정상 입력 예산은 최소한 **측정 간격 + 검증한 전달·계산 지연 + 시계 불확실성**을 포함해야 한다. 계단 벽·끝까지 남은 여유와 실측 기체 반응 시간보다 큰 예산을 허용하지 않는다. 두 조건이 양립하지 않으면 속도/계산 배치를 조정한다.

프레임당 위치·yaw 변화 제한도 시간에 비례한 비교와 예측 대비 보정량으로 바꾼다. 예를 들어 `v_bound·Δt + εp`, `ω_bound·Δt + εψ`를 진단에 사용하되, bound는 실제 이동·미끄럼을 포함해 검증한다. 명령 속도와 다르다는 이유만으로 실제 미끄럼 관측을 버리지 않는다. LiDAR용 설정을 별도 파일에 두어 legacy wheel mode와 NAV 조건을 함께 느슨하게 만들지 않는다.

<span id="5-직진계단참-회전의-구체적-제어"></span>

## 5\. 직진·계단참 회전의 구체적 제어

**제안:** 계단 profile에 진입 기준, 각 구간의 목표선, 계단참 회전 영역, 출구 경계의 기하를 연결한다. 녹색 bag 경로는 초기 검토 자료로 사용할 수 있지만 그 경로 자체가 중앙선이라는 전제는 두지 않는다. 실측 중심선·벽 경계와 대조한다.

첫 상행 구간의 목표 진행 방향을 `ψref`, 그 선으로부터 왼쪽 이탈을 `ey`로 정의한다. 제어는 다음 단순식에서 시작한다.

`eψ = wrap(ψ − ψref)`

`ωcmd = clamp(−kψ·eψ − ky·ey, −ωlimit, +ωlimit)`

기체의 실제 yaw 명령 부호·응답을 평지에서 먼저 확인한다. 작은 오차에는 관측 노이즈에 맞춘 deadband를 적용하고, 각속도와 그 변화량을 제한한다. yaw 오차나 측면 이탈이 커질 때 전진 속도를 줄이며, 정상 중앙 구간에는 추가 정지 조건을 넣지 않는다. 기존 전진 속도 0.40m/s가 새 보정과 함께 적절하다는 전제는 두지 않는다. 보정 gain·deadband·속도는 실측 후 확정한다.

이 식은 **상행 전진용 초기 설계**다. 후진 하행에는 그대로 적용하지 않는다. 현재 transport의 횡이동 출력은 `y=0`이므로, 이 범위의 측면 보정은 yaw와 전진으로 수행한다. 로봇 기체의 무게중심·다리/바퀴 자세를 직접 제어하는 기능은 아니다. 계단 모드에서 상위 yaw 명령이 실제로 의도한 효과를 내는지 별도 측정한다.

**앞뒤 밀림과 대기 위치 유지도 피드백에 포함한다.** 신선한 LiDAR의 기체 위치를 목표 진행선에 투영한 진행 좌표를 `s`, 시간 구간의 실제 속도를 `v_hat`으로 둔다. 상행 중에는 우선 `v_cmd = clip(v_nom + kv·(v_nom−v_hat), v_min, v_max)` 형태의 제한된 속도 보정을 시험한다. 진행이 둔하다는 이유로 명령을 계속 키우지 않도록 여유·상태에 따른 상한과 변화율을 두며, 접촉/걸림과 미끄럼의 구별이 안 되는 구간은 이 식만으로 해결했다고 판단하지 않는다. 수치 미분은 관측 간격·신뢰도·잡음에 맞게 필터링하고 지연을 기록한다. 이 식과 gain은 검증 전 제안이다.

기체 전체가 들어온 **계단참·출구 평지**에서는 고정 목표 `s_hold`에 대해 `v_cmd = clip(ks·(s_hold−s)−kd·v_hat, −v_hold, +v_hold)`를 초기 후보로 사용한다. 작은 오차에는 deadband, 보정 시작/종료에는 hysteresis를 둔다. 후진 보정은 해당 위치의 경계 여유와 실제 응답이 검증된 범위에서만 허용한다. 회전 중에는 매 시각의 기체 전방축에 위치 오차를 투영하고, 전체 회전 외곽이 계단참 안에 있는지 함께 평가한다. 횡방향 오차는 v/ω만으로 즉시 제자리 복원할 수 있다고 가정하지 않는다. 필요 이동 궤적과 회전 여유를 검사해 가능한 범위의 작은 경로 보정으로 처리한다. 밀린 위치로 hold 목표를 계속 옮기지 않는다.

**계단 중간은 평지 hold와 다르다.** 단 위의 임의 위치를 정지 목표로 지정하고 뒤로 되돌리는 동작은 이식 범위에 넣지 않는다. 정상 등반은 경계와 다음 구간 정렬이 확인되는 대로 이어가며 불필요한 zero dwell을 줄인다. 계단참에서 정렬·위치 확인을 위해 대기하는 동안은 명령 0이 아니라 실제 위치 범위·속도·자세 변화를 평가한다. 제어가 관측보다 빠르게 반복되어도 같은 5Hz pose를 새 관측처럼 세지 않는다.

**기울어짐의 책임 범위:** 현재 [transport 208행](/home/m3tron/Desktop/TRON1_Control/TRON1_RViz_Navigation/src/stair_supervisor/src/stair_supervisor/robot_transport.py#L208)과 [명령 변환](/home/m3tron/Desktop/TRON1_Control/TRON1_RViz_Navigation/src/stair_supervisor/src/stair_supervisor/robot_conversion.py#L32)은 전진·yaw 입력을 연결한다. 여기에는 roll/pitch·다리 토크를 직접 지정하는 경로가 없다(OBSERVED). IMU의 기체 기준 각속도와 단기 자세 변화는 악화 감지·기록에 쓰지만, pitch 하나를 속도 명령으로 비례 변환하지 않는다. 장시간 자세를 순수 자이로 적분으로 확정하거나 동적 가속도를 곧바로 중력으로 해석하지 않는다. 기존 펌웨어의 자세 유지 기능과 허용 명령을 설치 자료·실기 응답으로 대조한다. 상위 v/ω 보정으로 기울어짐까지 해결되는지는 UNVERIFIED이며, 별도 저수준 인터페이스가 불가피하면 범위와 이유를 먼저 보고한다.

## 6\. 도착 판단과 짧은 측위 결손의 처리

**제안:** 도착은 다음 증거를 순서대로 확인한다. 시간표시 `FINAL_ARRIVAL`은 어느 단계에도 입력하지 않는다.

  - 실제 관측한 경사 구간을 통과했고, 마지막 단/계단참 경계와 출구 방향의 평지 범위를 확인한다.
  - 변환한 기체의 지지 영역이 경계 너머에 있고, 다음 정지 위치까지 지지 가능한 공간이 있다. 앞쪽 LiDAR가 평지를 본 것만으로 완료하지 않는다.
  - pitch·높이 변화는 보조 증거로 사용하고, 위치 범위와 속도를 시간 구간에서 확인한다. 하나의 pose 반복 수신으로 dwell을 채우지 않는다.

초기 구현은 **실측된 계단 경계와 profile을 이용하는 방식**으로 범위를 줄인다. point cloud에서 평지·마지막 단을 자동 추출하는 부분은 기존 bag의 가림/점 밀도로 성립하는지 먼저 확인한다. 그 증거가 없으면 일반화된 자동 계단 인식을 구현했다고 보고하지 않는다. 추정 종료 위치는 외부 영상/실측과 따로 대조한다.

짧은 정합 결손은 `DEGRADED` 진단과 관측 나이로 표시하고, 완료 판정에는 사용하지 않는다. 검증된 유효 기간 안의 최신 관측을 다시 송신하는 것과 오래된 pose에 최신 stamp를 찍는 것은 구분한다. 기하 관측이 회복되고 epoch·위치 연속성이 맞으면 같은 phase에서 자동 복구한다. 단 한 프레임 결손으로 현행 `_latch_fault()`처럼 socket을 닫고 재시작을 강제하지 않는 방향이다.

**확정한 설계 전제:** 사용자 현장 보고에 따라 zero를 지지·정지 보장으로 사용하지 않는다. 관측 만료 시 사용할 `loss_response`는 현 위치의 지지 조건과 기체가 실제로 지원하는 동작으로 검증해야 한다. 현재 v/ω 인터페이스에서 어떤 명령이 계단 중간의 밀림·기울어짐을 억제하는지는 아직 UNVERIFIED다. 임의의 약한 전진, 자동 stair 해제, emergency-stop 요청도 검증 없이 안정 자세로 간주하지 않는다. 이 미확인 조건은 core 이식·오프라인 회귀·관측 운용을 막지 않는다.

**제안하는 추적 상태별 명령 계약**은 다음과 같다. `T_warn`, `T_expire`, `T_recover`는 정상 센서 지연과 기체의 실제 반응·지지 여유로 현장 제어 전에 확정한다. 현재 core의 진단용 0.5초를 이 시간들로 그대로 전용하지 않는다.

| 내부 상태                                       | 실제 명령 선택                                                                                                                 | phase와 복구                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| TRACKED, 관측 나이 ≤ T\_warn, 결손·거절 없음          | 목표선 피드백의 제한된 v/ω                                                                                                         | 새 기하 관측만 진행·완료의 근거로 사용                                                                       |

상태 선택은 **통신/복구 실패 → frame 불연속 → 관측 만료/worker 실패 → 일시 지연·결손 → 정상** 순서로 한 분기만 택한다. 관측 만료는 `age ≥ T_expire`이고 유효 관측이 없으면 age를 무한대로 취급한다. 새 scan 미도착도 나이가 계속 증가하므로 같은 분기를 따른다. 수락됐지만 늦게 계산된 scan을 정상 분기로 우회시키지 않는다.

독립적인 현장 보호 조건을 갖춘 M4의 제한된 제어 시험으로 응답과 복구를 계측한다. 그 시험 전 일반 운용은 observe로 두고, `loss_response`를 검증하기 전 무인 계단 control 운용을 수락하지 않는다. 이는 해당 계단 적용 범위이며 기존 정상 NAV를 전역 차단하지 않는다. M4에서 복구 시간·지지 가능한 위치·인계 방식을 확정한다.

현재 transport watchdog은 입력이 오래되면 zero를 보낸다. 이를 삭제하거나 오래된 nonzero를 무제한 반복하게 만들지 않는다. 새 제어 루프는 정상 주기로 명령을 갱신하고, **명령 만료와 신체 안정 상태를 별개로 기록**한다. 상위 루프 정지·socket 단절 시에는 같은 상위 루프의 피드백으로 복구를 보장할 수 없으므로, 기체 측 watchdog·자세 대응과 인계 시간을 따로 시험한다. 실제 확인 전에는 이 경우를 안전하게 멈춘 것으로 판정하지 않는다.

## 7\. 도착 후 위치 유지와 범위 경계

**OBSERVED:** 현재 `_finish()`는 zero를 보내고 stair mode를 끈 뒤 NAV로 복귀한다. 능동 위치 유지는 구현되어 있지 않다. [현재 종료 처리](/home/m3tron/Desktop/TRON1_Control/TRON1_RViz_Navigation/src/stair_supervisor/src/stair_supervisor/supervisor.py#L218).

사용자의 최종 요구인 ‘도착 지점에서 밀리면 되돌아와 대기’는 후속 묶음으로 포함한다. 계단을 완전히 벗어난 평지에서 같은 측위로 실제 밀림을 관측하고, **기존 NavigationExecutor로 지정점 복원이 요구 오차 안에 되는지 먼저 시험**한다. 기존 최소 변경 계획과 같이 이것이 통과하면 mission 안의 낮은 우선순위 감시가 기존 NAV를 직렬 재사용한다. 진입 거리 `r_on`, 종료 거리 `r_off < r_on`, 방향 허용 범위는 실측 후 정하고, 작은 흔들림마다 보정하지 않는다. 유효한 지도 위치가 필요한 기존 NAV의 조건을 local 측위만으로 충족했다고 처리하지 않는다.

기존 NAV가 정밀도·좁은 공간·저속 응답을 충족하지 못할 때만 **같은 Supervisor 내부의 전용 위치 유지 제어**를 별도 변경안으로 확정한다. 어느 방식이든 새 명령·명시 정지가 들어오면 이전 보정과 child 실행을 정리하고 한 소유자만 송신하도록 인계해야 한다. 현재 mission은 NAV 상태를 명시적으로 확인하므로 HOLD 상태 숫자 하나를 추가해 연결을 깨뜨리지 않는다. 도착 action 결과와 대기 제어 수명을 분리해 완료가 영원히 대기하지 않게 한다.

따라서 첫 묶음은 ‘측위·계단 제어·실제 출구 확인’, 다음 묶음은 ‘평지 HOLD와 mission 인계’다. **첫 묶음 통과를 전체 요구 완료라고 보고하지 않는다.** HOLD의 구체 API·변경 파일은 이식 검증 결과와 대기 허용 거리 확인 뒤 별도 상세 변경안으로 확정한다.

**첫 묶음에도 종료·취소 인계는 포함한다.** 다음 묶음으로 남기는 것은 장시간 HOLD의 실행·중단을 mission과 연결하는 기능이다. M5 종료 시에는 출구 지지 평지의 임시 위치 보정을 유지한 상태에서 다음 명령 소유자의 준비와 mode 전환 중 위치 변화를 확인한다. 이 첫 시험의 후속 소유자는 미리 지정한 기존 NAV 또는 운전자이며, 단순 ‘NAV 준비됨’이나 zero 수신만으로 위치 유지 성립을 판정하지 않는다. 후속 제어가 준비되지 않으면 성공 완료 후 무소유 상태로 방치하지 않고, 미리 정한 인계 시간 안에 확인된 기체 대응과 운전자 인계로 전환한다. 장시간 무인 도착 대기 요구는 M6까지 통과해야 충족된다.

계단 중 취소 요청은 새 진행 목표를 즉시 중단하고 해당 지지 조건에서 검증한 `loss_response`를 선택한다. 이를 출구 도착으로 처리하거나 `_finish()`를 그대로 호출해 stair mode를 끄고 NAV에 넘기지 않는다. 기존 cancelled 결과에는 취소 사실을 반환하고, 물리적 인계가 끝나기 전 명령 소유권은 Supervisor에 남긴다. command/watchdog 갱신과 별도 인계 timeout도 유지한다. 기체가 지원하지 않는 정지·자세 유지나 취소 뒤 임의 전진을 약속하지 않는다. 현장 제어 전에 기존 mission의 child 취소·timeout 처리와 이 동작이 일치하는지 T14에서 확인하며, 현 구조에서 결과/소유권을 분리할 수 없다면 필요한 최소 변경을 먼저 보고한다. 통신 단절에서는 전달되지 않은 대응 명령을 실행 완료로 기록하지 않는다.

수락 판정의 수치 산정도 미리 고정한다. 실측 통로와 동적 기체 외곽 사이 최소 여유를 `C`, 외부 측량/영상 오차를 `εref`, 장착·측위 불확실성을 `εpose`, 응답 지연 중 이동 여유를 `Dresponse`라 하면 허용 측면 오차는 `Eallow ≤ C−εref−εpose−Dresponse`로 정한다. 결과가 양수가 아니면 그 조건에서 중심 유지가 가능하다고 승인하지 않는다. 외부 영상은 실측 기준점으로 축척·자세·시각을 맞추고, 기체 전체 외곽/지지 영역을 그 기준에서 평가한다. M4 전에 수치를 기록하고 평가 결과를 본 뒤 기준을 넓히지 않는다.

평가용 초기 제안은 **측면 오차 최대 ≤ Eallow, P95 ≤ Eallow/2**이며, yaw 허용오차는 다음 구간에서 그 기체 외곽이 통로를 침범하지 않는 범위로 정한다. 흔들림은 eψ/ey의 부호 반전과 피크 크기·감쇠를 외부 관측으로 함께 확인한다. 반복 보정의 피크가 감소하지 않거나 기체 여유를 소진하면 튜닝 통과로 보지 않는다. 이 숫자들은 운용 중 매 순간 새로 적용하는 정지 gate가 아니라 시험 수락 기준이다.

명령 송신은 목표 40Hz와 함께 **송신 간격 P99 ≤ 33.3ms, 관측된 최대 ≤ 50ms**를 첫 부하 시험의 공학적 목표로 제안한다. 제조사/실측 요구가 더 엄격하면 그것을 적용하며 이 목표를 기체의 공식 watchdog 사양이라고 주장하지 않는다. scan 처리 P99만으로 이 항목을 PASS 처리하지 않는다. 완료 시간은 사전 측정한 실제 속도·회전·의도된 dwell로 구한 `Tnom`에 대해 `1.25×Tnom + 사전 확정 복구 예산` 이내, 그리고 승인된 전체 timeout 이내로 정한다. 정상 조건에서 의도된 dwell 외의 불필요 정지 횟수·누적 시간은 0을 목표로 한다. 복구 시간도 T\_recover 안에 들어야 하므로 무한 대기·과도한 감속으로 안전 항목만 통과할 수 없다.

M3에는 두 운용 방식을 구분한다. 이미 기존 Supervisor가 명령을 소유하는 시험에서는 새 측위를 옆에서 계산해 비교한다. 사람이 별도 조종기로 운전하는 시험에서는 Supervisor의 **관측 전용 시작 경로**가 RobotTransport/socket을 만들지 않게 한다. 단순히 제안 속도를 0으로 보내는 것을 관측 전용이라고 부르지 않는다.

측위 코드를 bag으로 검증해도, 그때 계산한 새 조향 명령이 실제 로봇의 미래 움직임을 바꾸었을 때 결과는 알 수 없다. 따라서 bag에서 계산한 측면 오차 감소나 명령 방향을 **폐루프 주행 성공률**로 보고하지 않는다.

## 12\. 디버깅·적용·복구

진단 한 행에 실행 ID/epoch, phase, 센서 시각, 관측 나이, queue 길이/누락 수, compute 시간, 실제 pose, 목표선, `ey/eψ`, 진행 좌표·실제 속도·hold 오차, 기체 기준 각속도·단기 자세 변화, 제안/실제 송신 명령, watchdog 상태, 정합 사유와 phase 전환 사유를 함께 기록한다. 로그는 크기 제한·회전 정책을 두며, 전체 원시 점군을 상시 무제한 복사하지 않는다. 원시 센서·진단·실제 `/stair_supervisor/websocket_tx`를 같은 bag에 기록해 재현한다.

RViz에는 현재 관측, 목표선, 기체 외곽, 계단참/출구 경계, 실제 Supervisor phase와 추적 상태를 보여준다. 수동 영상 표식은 별도로 명시한다. pose 품질이 나쁘면 표시만 정상처럼 유지하지 않는다.

첫 배포 기본값은 `off`, 다음은 `observe`, 최종 검증 profile에 한해 `control`이다. 모드는 실행 중 자동 변경하지 않는다. 배포 전 실제 host의 설치 소스/의존성/보정 해시를 대조하고, 운용 중이 아닌 시점에 이전 버전으로 되돌릴 수 있게 한다. 새 측위 실패 때 계단 중 조용히 legacy wheel 제어로 바꾸는 것을 rollback으로 취급하지 않는다.

**외부 API 구분:** 이 문서의 phase·fault·ownership 설명은 repository 코드의 동작이다. ROS Timer는 설치된 Noetic [timer.py 190행 부근](/opt/ros/noetic/lib/python3/dist-packages/rospy/timer.py#L190)에서 별도 thread로 구현됨을 확인했지만, 그 사실이 실시간 deadline 충족을 보장하지는 않는다. 현재 실장비 ROS graph·PC 계산 성능·기체의 실제 응답은 이번 계획에서 관찰하지 않았다.

## 13\. 반영한 답변과 이번 작업의 완료 범위

실행 위치와 zero 동작에 대한 재질문은 종료했다. 사용자 정정과 기존 자료를 다음처럼 반영했다.

1.  **배치 확정:** 기존 제어 PC의 Supervisor 내부. 다른 manager/move\_base와 함께 부하 시험한다.
2.  **현장 조건 채택:** stair mode+zero로도 밀림·기울어짐이 생김. zero-hold 가정 삭제, 필요한 계단참·출구 위치 보정은 첫 제어 묶음에 포함한다.
3.  **기존 기하 복구:** 폭 1.23m, 계단참 2.70×1.48m, 5F→RF 10단+9단+출구 2단. 층별 원본 연결과 아직 찾지 못한 치수는 자료 대조 대상으로 관리한다. 제공한 치수를 전부 다시 요청하지 않는다.

남은 것은 새 배치 선택이 아니라 기체 인터페이스·동적 지지 영역·기하의 층별 대응·실제 보정 응답을 확인하는 작업이다. 원본 자료를 확인한 뒤에도 사용자 판단이 필요한 항목만 구체적으로 질문한다.

Safety verdict: **UNVERIFIED**, 실장비 피드백 제어·완전한 출구 통과·유실 시 기체 지지 대응은 아직 검증되지 않았다. 특히 zero로도 밀린다는 현장 보고를 해결한 것으로 취급하지 않는다.

Mobility verdict: **OBSERVED**, 기존 입력 계약은 좋은 5Hz 추적을 즉시 fault로 만들 수 있다. 제안은 이 충돌을 제거하고 기존 명령 경로 안에 보정을 넣는 것이다. 실제 성공률 개선은 **UNVERIFIED**다.
