# v22: 상승 조향 방향의 시점 정합과 충격 완화

## 수정한 문제
OBSERVED: observed_feedback 상승 정책은 IMU로 현재에 가까운 방향(control_yaw)을 계산해도 조향 오차에는 원래 LiDAR 관측의 yaw를 사용했다. 03:23 BAG의 03:24:10.780에서 LiDAR yaw는 -7.1도, 받은 IMU까지 갱신한 방향은 +4.9도였고, 조향은 이전 방향을 따라 풀리고 있었다. 최신 방향이 실제 절대 참값이라는 뜻은 아니지만, 이미 갖고 있는 시점 갱신 결과가 조향에 반영되지 않는 코드 경로는 확인했다.

이제 observed_feedback 상승에서 연속적으로 받은 IMU의 마지막 데이터가 기존 신선도 기준 안이면 해당 갱신 방향을 조향에 사용한다. IMU는 각 LiDAR 관측에서 다시 시작하는 짧은 구간 적분이며, 입력이 끊기거나 늦으면 LiDAR 방향으로 돌아간다. 장시간 IMU 단독 측위나 미래 데이터 추정은 추가하지 않았다.

계단 충격으로 방향이 순간 반전할 때 조향이 반복적으로 풀리는 것을 줄이도록, 조향용 방향에 시정수0.25초의 원형 1차 필터를 적용했다. 매 제어 주기 명령을 계산하며 0.25초간 정지하고 기다리는 방식은 아니다. 이 값은 시험용 조정이며 최적값을 실측해 확정한 것이 아니다. 필터에는 실제 방향 변경의 반응을 늦추는 tradeoff가 있다.

원래 LiDAR pose, 차체 지지영역, 높이·자세, 입력 유효성 및 도착 관측은 필터링하거나 재작성하지 않는다. 추정 방향으로 과거 위치의 footprint를 다시 돌려 지지 판정을 만드는 혼합도 하지 않는다. 센서 손실/새 phase/epoch/시간 역행 후에는 필터 이력을 초기화한다. gyro_used/source 진단은 현재 입력이 gyro인지 뜻하며 필터의 모든 과거 기여가 사라졌다는 뜻은 아니다.

## 적용 범위
3→4층, 5층→RF 경로의 상승 단계에 적용한다. 기존 FSM/노드를 추가하지 않았다. 최대 내부 조향0.2, 조향 증가율0.3, 중립 복귀율0.9, 상승 입력 하한0.55, 계단참 속도, v20 회전, v21 진입 전이는 유지한다. 기록된0.55는 실제 이동속도를 입증하는 측정값이 아니라 내부 명령이다.

## 독립 검토와 기록
sip/shower의 새 검토자는 필터 지연 tradeoff와 source 진단의 의미를 지적했다. 필터값의 유한·양수 조건은 기존 route validator가 검사하고, pose 유한성은 transform()이 검사함을 확인했다. 재생 결과는 물리 성능 검증과 분리했다(mandela: 설계자/검증자 및 추정 자세의 공통 편향). 이 문서의 외부 하드웨어 원인은 확정하지 않았다. ssotize 점검상 제어 정책의 원본은 기존 stair_feedback.py, 조정값의 원본은 기존 yaml이며 새 노드/중복 설정 경로는 만들지 않았다.

원본 변경: stair_feedback.py, stair_lidar_3f_4f_test.yaml, 신규 test_flight_heading.py. 기존 worktree 변경을 보존했다. 임시 배포 파일은 제거하고 수정 전 파일·시험 코드·JSON·로그는 분석 근거로 보존한다. 원본 BAG을 바꾸지 않았고 로봇/문 제어 명령을 보내지 않았다. 실행 중 스택은 재시작하지 않았다. 새 코드 적용에는 재시작이 필요하다.
