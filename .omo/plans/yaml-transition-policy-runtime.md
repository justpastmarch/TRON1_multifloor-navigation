**What you'll get:** The transition YAML will become a real runtime policy instead of dead configuration. Its three current safety conditions will be explicit 0/1 entries, fixed as enabled and required, while freshness, dwell, and timeout are enforced without allowing the robot's existing map, localization, cancellation, or costmap safety order to be bypassed. There are no current non-safety conditions. The same list format can accept one later only after its semantics, authoritative producer, and registry entry are explicitly added.

**Why this approach:** The current floor manager already owns the safe transaction, so policy is added only as a final extra gate inside that manager. All policy data and pure timing logic live in one small module; configuration only parses, runtime only synchronizes epoch-owned state, and the node keeps one explicit final-gate helper. Conditions stay pure and repeatable; future commands such as opening an automatic door must be separate typed actions so a dwell check cannot accidentally transmit a command multiple times.

**What it will NOT do:** It will not add another ROS node, weaken fixed safety barriers, activate untuned production data, or introduce automatic-door/network command execution. It will not allow arbitrary shell commands, URLs, or IP payloads in YAML.

**Effort:** Large
**Risk:** High - this policy sits on the terminal success path of an irreversible map/localization transaction, so stale evidence, cancellation, and parsed-but-unused false greens must be disproved.
**Decisions to sanity-check:** One fixed policy ID (`floor_transition_ready`), independent of stair IDs; mandatory safety aggregates remain enabled+required; floor confirmation is an epoch-latched event while localization and costmap readiness are live levels; policy timeout begins only when the final gate starts; future side effects are typed actions, not conditions.

## Scope
### Must have
- Replace transition-level `enabled: bool`, `required: [...]`, and `optional: [...]` with one ordered condition list. The outer `configured` document flag remains a YAML Boolean; policy and condition `enabled`/`required` fields are exact YAML integers `0` or `1` and are converted to typed booleans only after validation.
- Retain `optional_count`, `freshness_sec`, `dwell_sec`, and `timeout_sec` with explicit runtime semantics and strict path-qualified errors.
- Require exactly one policy with ID `floor_transition_ready` in any configured document.
- Support exactly the current aggregate registry `T_FLOOR_CONFIRMED`, `T_LOCALIZED`, and `T_COSTMAP_READY`; all three are safety-critical, must appear once, and must be enabled+required, so the current configured policy requires `optional_count: 0`. Unknown names fail startup. There is no current optional/non-safety predicate. `optional_count` remains implemented and unit-tested because it is part of the approved YAML contract, but it stays zero unless a future condition is explicitly classified non-safety and gains a typed producer plus registry entry.
- Move the pure evaluator/domain types to `multifloor_manager` so the dependency remains `mission_manager -> multifloor_manager` and never reverses.
- Keep production ownership explicit and small: `transitions.py` owns policy types/evaluation only; `configuration.py` owns strict YAML conversion only; `ros_runtime.py` owns one synchronized manager/observation state with thin token-checked methods; `ros_node.py` owns transaction orchestration and one `_wait_for_policy_ready()` helper. Do not duplicate policy rules across these files.
- Keep the existing tag -> map generation -> landing pose -> causal AMCL -> localization -> costmap clear -> new target costmap sequence as fixed code-owned barriers.
- Return an immutable epoch token from `arm_transition()` and require that token for every node-thread policy record/evaluate/commit. Invalidate policy state on success, failure, timeout, and cancellation. Missing, false, future-dated, stale, or mismatched-epoch observations evaluate false and cannot be attributed to a later rearmed transaction.
- Apply policy only after the fixed post-clear target costmap barrier and before `FloorState.READY`/action success. Policy may delay or reject success but cannot authorize an earlier operation.
- Treat `T_FLOOR_CONFIRMED` as one epoch-latched event timestamped when the target-tag wait releases. Treat `T_LOCALIZED` and `T_COSTMAP_READY` as live levels that are resampled on every final-gate iteration and explicitly overwritten false when their current source is false.
- Define the successful second `is_preempt_requested()` check as the action decision point. A cancellation observed by that check wins; a request arriving after it loses, and the epoch-matched READY commit plus `set_succeeded()` proceed without another cancellation branch. Do not claim atomicity between actionlib's private lock and the runtime condition.
- Prove runtime consumption with two real ROS action surfaces: the normal fixture succeeds; an otherwise equivalent blocked-policy fixture reaches no `READY` and aborts.
- Keep production `src/multifloor_manager/config/transitions.yaml` at `configured: false`.
- Keep one comment-only non-safety placeholder in production YAML and operator docs. It is not a configured condition and must remain commented until a pure producer, registry entry, and tests exist; copying it into a configured policy's `conditions` before support must fail as an unknown predicate.
- Document that current safety flags cannot be changed and that no non-safety condition currently exists. For each future condition, require an explicit safety classification before registry admission: safety conditions are fixed required; only genuinely non-safety conditions may be optional/quorum-controlled. Side-effecting commands remain typed, allowlisted manager actions with separately validated device identities.

## Verification strategy
> Zero human intervention - all verification is agent-executed.
- Test decision: TDD. Use `unittest`/catkin nosetests for schema and evaluator, existing rostest/actionlib fixtures for runtime behavior, and the existing catkin build/test surface for regression.
- Source authority: direct tests must prepend `src/*/src` exactly as `test/test_site_configuration.py:11-15` does. `devel/` and `install/` are build outputs, never implementation authority.
- Temporal and concurrency semantics:
  - `PredicateObservation(value, observed_at_sec, epoch)` is internal typed evidence; the policy still consumes Boolean block outputs after epoch/freshness filtering.
  - `freshness_sec` means `0 <= now_sec - observed_at_sec <= freshness_sec`; stale, missing, or future-dated observations are false.
  - `dwell_sec` requires continuous instantaneous truth and resets immediately on any false/stale/missing observation.
  - `timeout_sec` starts when the node enters `POLICY_READY`, not at transaction arm; existing tag/service/map/localization/costmap deadlines remain independent. Equality at the policy deadline is timed out, success must occur strictly before it, and schema validation requires `0 <= dwell_sec < timeout_sec`.
  - `T_FLOOR_CONFIRMED` is an epoch-latched event timestamped when the accepted target tag vote releases the pre-map wait.
  - `T_LOCALIZED` and `T_COSTMAP_READY` are levels. Every final-gate loop iteration records their current true or false value; a false sample immediately resets policy dwell. Localization is recomputed through `localization_evidence().ready`; costmap readiness is recomputed from the post-clear sequence marker and current target metadata.
  - Policy age/dwell/timeout use monotonic time. Sensor freshness inside localization/tag evidence continues using ROS message/receive time; tests and docs must keep these clock domains explicit and reject future/backward values rather than silently mixing them.
  - `arm_transition()` returns the expected epoch token. Every node-thread record, final-gate evaluation, and READY commit carries it and rejects mismatch, including the finish-N/rearm-N+1 race.
  - The final-gate loop checks preemption before evaluation and once more after a true evaluation. The successful second check is the decision linearization point: cancellation observed there wins; requests arriving afterward lose. The code then performs the epoch-matched READY commit and `set_succeeded()` without another cancellation branch. The runtime lock protects epoch/state, not actionlib's separate preempt flag.
- Runtime proof: parser/evaluator tests are insufficient. One paired rostest must vary only policy configuration and produce opposite action outcomes while launching exactly the existing `multifloor_manager` production node.
- Regression proof: retain feedback ordering and all map, pose, costmap, epoch, late-map, delayed-pose, and cancellation assertions. New policy checks are additive.
- Simplicity proof: final review counts nonblank/noncomment lines and rejects duplicated validation/evaluation, unused abstractions, generic dispatch, or more than one new production Python module (`multifloor_manager/transitions.py`).
- Evidence root outside `omo ulw-loop`: `.omo/evidence/yaml-transition-policy-runtime/<task-id>/`. Each task writes `receipt.yaml`, `commands.txt`, `baseline.json`, `diff-inventory.json`, `test-results.txt`, and `cleanup.json`.
- Receipt minimum: plan slug, stable task ID, attempt ID, dependency receipts, allowed/changed paths, source and generated digests, exact commands/exit codes, happy+failure results, cleanup, and next safe tasks. A missing dependency receipt, unexplained path change, stale generated import, or un-attributable cleanup yields `needs-fix`; unavailable hardware/site data yields `blocked`.
